加解密流程

一句话：你只管「编辑保存」和「查看复制」；加解密、验章、上传拉取全部由客户端在后台自动完成，服务端只收密文。

写入一条密码：加密

人操作 1 步后台自动 4 步
1
人操作你编辑条目 → 点保存
在树中选到账号节点（项目→环境→IP类型→账号类型→账号），编辑密码 / 备注，填好保存。之后发生的一切都不需要你再管。
2
后台自动客户端取该组 DEK
从内存缓存取 group_id 对应的 DEK；没有就先用私钥解自己的信封。DEK 永不出内存、不上云。
3
后台自动客户端SM4-GCM 加密
随机 nonce(12B) + SM4-GCM(DEK, nonce, AAD=entry_id+group_id) → 密文。nonce 每次随机，同样明文两次结果不同。
4
后台自动客户端加 HMAC 防伪章
HMAC-SM3(派生密钥, entry_id|group_id|kv|nonce|ct) → hmac，用来在解密时发现"密文被篡改/回滚"。
5
后台自动客户端→ 服务端push 密文包
组装 {v, alg, kv, nonce, ct, hmac} 经 TLS1.3 上传。服务端只存密文，不解密、不索引。
1 / 5

读取一条密码：解密

人操作 1 步后台自动 4 步
1
人操作你解锁 → 点击查看条目
解锁时输入 keyfile 口令；之后在树中点开要查看的账号，剩下的都是后台自动。
2
后台自动客户端← 服务端增量拉取密文 + 信封
按 last_seq 拉取本组变更（SSE 推送或启动自动拉取触发）；服务端只返回密文和信封。
3
后台自动客户端解信封拿 DEK
用 SM2 私钥解自己的信封 → DEK。若密文包的 kv 比本地新（发生过重加密），先拉新信封再解。
4
后台自动客户端验 HMAC 防伪章
HMAC 不符 → 判定密文被篡改/是脏数据，记入 bad_seq 跳过清单不阻塞其他条目；同一 seq 连续 5 次失败则重试一次，仍失败写入本地告警日志并在 UI 标记"该条目同步异常"，需手动处理。
5
后台自动客户端SM4-GCM 解密 → 展示
解出明文（未知字段 json.RawMessage 保留）；明文只在内存，锁屏清零，复制后剪贴板 30 秒自动清空。
1 / 5
为什么服务端被攻破也不泄露？ 服务端只有密文 + 信封。信封要用私钥解（私钥在成员本地、口令保护），密文要用 DEK 解（DEK 也要私钥才拿得到）。拖库 = 一堆没有钥匙的密文。

新人加入 · 无感入伙（auto-wrap）

一句话：admin 只需要 3 次人操作（生成密钥、建用户加组、转交文件），剩下的密钥交接全部后台自动，新人也就 2 次人操作（导入、输口令）。

新人加入全程

人操作 5 步后台自动 3 步
1
人操作admin本机生成密钥（一条命令）
keytool genuser --name 新人：产出 keyfile（私钥）+ pub.json（含注册凭证 attestation）。私钥不经过服务端。
2
人操作admin→ 服务端管理页创建用户
导入 pub.json → POST /admin/users。随后的「校验 attestation、登记公钥」由服务端后台自动完成。
3
人操作admin一键加组
PUT /admin/groups/:gid/members。至此新人已是组成员，但还没有信封（暂时解不了 DEK）。
4
后台自动在线成员客户端auto-wrap：自动包裹信封
SSE 推送 ~1s 内发现 missing_envelopes=[新人] → 用组 DEK 包裹新人的公钥 → POST /groups/:gid/keys（kv 不变，仅追加）。无任何老人手工操作。
5
人操作admin线下转交 keyfile
把 keyfile + 口令分两条安全通道转交新人（U 盘 / 加密聊天，口令另走一条）。
6
人操作新人导入 keyfile 并解锁
导入 keyfile → 输口令 → 派生 KEK → 解出 SM2 私钥（驻留内存）。
7
后台自动新人客户端→ 服务端设备注册
取 challenge → 私钥签名 → 服务端用登记的公钥验签 → 发 device token。持 keyfile 即证明身份，全程无感。
8
后台自动新人客户端启动自动拉取 → 解密使用
启动即增量拉取 → 拉到自己的信封 → 私钥解出 DEK → 解密组内条目。到这里新人就能正常用了。
1 / 8
关键点：最核心的「包裹 DEK 信封」这一步（第 4 步）是后台自动完成的——所以加人不需要任何老人在线配合手工操作，新人也不需要懂任何密码学。
3

老人退出 · 即时断权 + 自动重加密（auto-rekey）

一句话：admin 只需 1 次人操作（点一下吊销/移出），其余断权、重加密、删旧信封全部后台自动，被移除者瞬间读不到任何新数据。

老人退出全程

人操作 1 步后台自动 6 步
1
人操作admin一键吊销 / 移出
POST /admin/users/:uid/revoke 或 DELETE /admin/groups/:gid/members/:uid（需输入对象名二次确认）。就这一步需要人。
2
后台自动服务端立即断权（单事务）
token 全部失效 + 移除组成员 + 删除该成员全部信封 + 置 pending_rekey=1。不依赖任何人在线，即刻生效。
3
后台自动在线成员客户端收到通知，检测 pending_rekey
SSE 推送 ~1s 内发现该组待重加密 → 自动进入 auto-rekey 流程。
4
后台自动在线成员客户端写挂起该组新写入
关键不变量：重加密完成前，该组新数据绝不用旧 DEK 加密——新写入只进本地队列，不出网。
5
后台自动在线成员客户端换新 DEK（kv+1）+ 新信封
用旧 DEK 解出全部条目 → crypto/rand 生成新 DEK → 为全部 active 成员包裹新信封 → 上传（服务端升 kv、清 pending_rekey、旧信封暂保留）。
6
后台自动在线成员客户端重加密全部条目并 push
用新 DEK 重加密全部条目（kv+1）→ push。服务端在条目全部换新后物理删除旧 kv 信封；崩溃可续跑。
7
后台自动被移除者从此读不到新数据
后续请求一律 40301/40302；即使手里还留着旧 DEK，也拿不到任何离职后的新密文。
1 / 7
不可违背的两点：① 断权即时——吊销那一刻起旧人连服务端数据都拉不到；② 写挂起——重加密完成前不会产生「用旧 DEK 加密的新数据」外流。全员离线时组写挂起，数据不丢，有人上线自动收敛。
4

冲突解决 · 字段级三路合并

一句话：两个人同时改同一条，不是整条二选一，而是像 Git 一样逐字段三路合并——只有真冲突的字段才需要你点一下。

冲突处理全程

后台自动 4 步人操作最多 1 步
1
后台自动客户端编辑前自动存快照 base
条目进入编辑状态时，若没有快照则存下当前明文（base_enc，KEK 派生密钥加密，本地），作为后续三路合并的"共同祖先"。push 成功后清除；再次编辑同一条目不覆盖。
2
后台自动客户端→ 服务端push 被拒（40901）= 发现冲突
push 时 base_seq != 服务端当前 seq → 返回 40901 并带上服务端当前版（theirs）。客户端把本地版转成"冲突副本"（ours），以服务端版为当前版。
3
后台自动客户端逐字段三路合并（纯函数）
以 fields 与 custom_fields 每个键为单位对比 base / ours / theirs：仅一方改 → 采用改方；两方都没改 → 保留原值；两方都改且值不同 → 该字段标冲突，其余字段正常合并。
4
人操作你只在有冲突字段时：三栏 diff 逐个选
无冲突字段 → 合并结果直接 push（一次成功），你完全无感。有冲突字段 → 进冲突解决页：三栏 diff（base / ours / theirs），每字段「采用本地 / 采用服务端 / 手动编辑」，解决后 push 一次。
5
后台自动客户端push 合并结果
以合并结果为新版本 push；成功后清 base 快照。被其他端删除的本地修改 → 提示"他端已删除此条"，可选丢弃或还原为新条目（新 entry_id 重新发布，避免与墓碑 40903 冲突）。
1 / 5
服务端零改动：三路合并全部在客户端完成——base 存在本地、theirs 来自 40901 响应，服务端始终只存一份最新密文。大多数冲突自动合并成功，只有真正的字段冲突才需要人介入。
5

keyfile 丢失找回 · 数据不丢

一句话：keyfile 丢了、口令忘了，admin 重新生成一份新的换绑即可——历史数据一条不丢，全程不需要任何成员手工配合。

找回全程

人操作 3 步后台自动 3 步
1
人操作admin生成新密钥
keytool genuser --name 原用户名 → 新 keyfile + pub.json（含新 attestation 注册凭证）。私钥不经过服务端。
2
人操作admin→ 服务端keyfile-reset 换绑公钥
POST /admin/users/:uid/keyfile-reset，携带新公钥 + 新 attestation。服务端校验 attestation（与创建用户相同逻辑），不匹配一律拒收。
3
后台自动服务端单事务：换钥 + 断旧设备
更新公钥 + 作废该用户全部设备（token 全失效）+ 删除其全部信封 + 置所在各组 pending_rekey=1。期间该用户无法登录，直到用新 keyfile 重新注册。
4
后台自动在线成员客户端auto-wrap 新公钥
检测到该用户新公钥无信封 → 用当前 DEK 为新公钥包裹信封（kv 不变，仅追加）。
5
人操作本人导入新 keyfile、重新注册设备
导入新 keyfile → 输新口令 → device-challenge + device（用新私钥签名）→ 获得新 token。
6
后台自动本人客户端→ 服务端拉取数据，恢复正常使用
GET /sync?since=0 → 拉到自己的新信封 → 解出 DEK → 解密全部条目。数据一条不丢。
1 / 6
边角：若找回的同时组里也在 rekey（第 3 步置了 pending_rekey），则 auto-rekey 与 auto-wrap 合并执行——先换新 DEK（kv+1），再为新公钥包裹新 kv 信封。

常见疑问：多人同时在线的并发

问：换 DEK 时如果多个成员同时在线，会不会都生成一个新 DEK、互相冲突？

① 信封层：服务端仲裁
kv+1 信封集合必须 = 全部 active 成员，且不许覆盖已有信封
② 条目层：乐观锁 base_seq
同一条目多人重推 → 40901 → 后者重拉丢弃，内容相同不构成分叉
③ 收尾：服务端事务内判定
全部条目到达新 kv → 清 pending_rekey + 删旧信封，谁推完谁触发
结论：只有一个成员的新 DEK 会被服务端采纳（其余 40904 后重拉收敛）；条目用乐观锁去重；收尾不依赖具体成员。即使有人崩溃、离线，旧信封保留 + 幂等续跑，最终都收敛到同一个 DEK'。兜底：服务端强制 key_version == 组当前 kv（40902），任何人都不可能用旧 DEK 写出新数据。

常见疑问：项目结束 · 断线 · 在线判定

问：项目结束了，组里的数据怎么办？能删掉吗？

答：admin 可以归档组（POST /admin/groups/:gid/archive，需输入组名二次确认）。归档 = 协作冻结 + 数据只读：push/信封提交被拒（40905）、SSE 不推送、auto-wrap/auto-rekey 全部冻结；但历史与信封照常可拉（换新设备也能只读查看），成员关系/信封/密文全部保留。期间吊销/移出成员即时断权有效，重加密挂起到重启后自动收敛。要重新启用时 unarchive 一键恢复，客户端检测到状态翻转自动全量拉取补齐。

问：SSE 断线了怎么办？会不会漏掉变更？

答：不会漏。SSE 只是"有更新的通知"，数据一律以加密拉取为准。断线后客户端指数退避重连（1s→2s→…→30s 封顶）；连续失败 10 次切为轮询模式（30s 间隔），每 5 分钟尝试恢复 SSE，恢复后立即增量拉取补齐。服务端同一 token 的 SSE 断开后 2 秒内不允许重连，防止抖动风暴。好网络下变更 1s 内可见，差网络下最多 30s 内收敛。

问：管理端怎么判断谁在线？设备要一直开着吗？

答：两种信号互补判定——①SSE 活跃连接：每 15s keepalive，在连接即在线；②心跳：客户端每 30s 上报一次 hostname（POST /auth/heartbeat），服务端更新 last_seen / last_ip / hostname。无 SSE 时 last_seen 在 60s 阈值内也算在线（容忍一次心跳失败）。管理端据此在组成员清单里展示"在线 / 离线 / IP / 机器名"。心跳失败不阻塞客户端主流程，静默重试。

问：新建的组，第一把 DEK 是谁生成的？

答：admin 建组时只建元数据，不生成 DEK。首个在线成员同步时发现"组内无任何信封"（冷启动）→ 本地 crypto/rand 生成 DEK（kv=1）→ 为全部成员包裹信封上传。多人同时发现时各自生成、服务端只采纳先到的那份（不许覆盖已有信封），后到者重拉收敛——同一套仲裁规则，全程无人手工操作。
