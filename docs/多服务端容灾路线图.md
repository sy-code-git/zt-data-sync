# 多服务端容灾路线图（二期 / 三期规划）

> 状态：规划稿（2026-08-14），待排期。目标：服务端"单点个人服务器"场景下的
> 人员离职迁移 + 宕机切换，尽可能无感 / 一键。

---

## 一、背景与目标

**现状约束**：服务端部署在组员个人服务器，域名 + 内网映射，域名/服务器均为个人资产
（非团队资产，DNS/LB 方案不可用）。备份服务**可有可无**（取决于团队配置）。

**目标**：
1. 人员离职 → 服务端可迁移到他人机器（一次性）
2. 个人服务器宕机 → 客户端可切到备用服务器（无感/一键）
3. 兼容「有备份」和「无备份」两种团队配置

---

## 二、核心设计原则

1. **客户端本地即权威备份**：`local_entries` 已存完整 `ciphertext + 明文 + seq +
   updated_at + base 快照`，天然可作数据重建来源。
2. **切换后自适应**：客户端连上新服务端后，**自动检测其数据状态**，决定走增量还是重建：
   - 新服务端 `server_seq > 0`（有数据）→ 正常增量同步
   - 新服务端 `server_seq = 0` 且本地有数据（空库）→ 触发全量重传重建
   - 这条检测逻辑让「有备份 / 无备份」**共用同一套客户端代码**
3. **手动切换优先，自动切换其次**：自动切换要处理"真宕机 vs 网络抖动"，边界多，先做手动，
   再做带阈值的自动切换。

---

## 三、分阶段路线图

| 阶段 | 内容 | 解决场景 | 优先级 | 改动面 |
|---|---|---|---|---|
| **P1** | 服务端迁移 SOP | 人员离职 | 文档为主 | 极小 |
| **P2** | 客户端多地址 + 手动/自动切换 | 宕机切换 | 核心 | 中 |
| **P3** | 管理端一键重定向 | 主动切换 | 高 | 中 |
| **P4** | 数据重建兜底（全量重传 + LWW） | 无备份的极端情况 | 兜底 | 中偏大 |
| **P0** | 定时备份脚本（可选） | 让备机有数据 | 视团队 | 极小 |

> P0 与 P4 是「可备份 / 不可备份」的两条互补路径：有备份走 P0+P2，无备份靠 P4 兜底。

---

## 四、各阶段简易方案

### P1：服务端迁移 SOP（零代码 / 少量文档）

**场景**：成员 A 离职，服务端从 A 的个人服务器迁到 B。

**方案**：写一份迁移 SOP，核心 =「停服 → 拷数据 → 新机拉起 → 客户端改地址」。

```
旧机：docker stop passbook-server
      tar czf passbook-data.tar.gz <数据目录>/passbook.db
      （同时带上 certs/ 与 PB_REG_SECRET 值）
新机：解压数据 → 放回 /data → docker compose up -d
客户端：设置页改服务端地址（现有 SetServerURL 已支持）
```

**改动**：仅文档（部署与迁移步骤见《编译与部署全流程》），无代码改动。

---

### P2：客户端多地址 + 切换（核心）

**场景**：主服务器宕机，客户端切到备用服务器。

**方案**：本地存地址列表 + 活跃地址，连接失败按阈值自动/手动切换。

| 层 | 改动 |
|---|---|
| store | 新增 `servers` 表（id/url/active/order），迁移 `0003`；`GetServers/SetServers/SetActiveServer` |
| core | `serverURL` 单值 → 地址列表 + 活跃索引 + `SwitchServer` |
| syncer | 连接失败（连续 N 次）→ 切下一地址重连；切换后触发一轮全量检测 |
| HTTPClient | 构造时用活跃地址（不变） |
| app.go / 前端 | 设置页地址列表管理（增删/测试连通/设为当前） |

**关键决策**：
- 手动切换先行（设置页选地址），自动切换加阈值（连续 3 次失败才切，防网络抖动误切）。
- 切换后**必须**触发 P4 的数据状态检测（空库 → 重建，有数据 → 增量）。

---

### P3：管理端一键重定向（主动切换）

**场景**：管理员预知主服务器要维护/迁移，主动一键切换。

**方案**：主服务端进入"重定向态"，向所有客户端下发新地址。

| 层 | 改动 |
|---|---|
| 服务端 | 重定向状态 + `POST /admin/redirect {target}`；心跳/同步响应注入 `redirect_to`；SSE 推 `server_switch` 事件 |
| 客户端 | 识别 `redirect_to` → 更新活跃地址 → 重连新服务端 |
| 管理端 | 「切换服务端」按钮 → 调重定向 API |

**流程**：管理端一键 → 主服务端下发重定向 → 在线客户端秒级切走 → 离线客户端下次上线自动切。

---

### P4：数据重建兜底（全量重传 + LWW）

**场景**：备用服务器**空库**（无备份团队配置），客户端本地数据重建服务端。

**方案**：客户端检测空库 → 全量重传本地条目 → 服务端 LWW 冲突合并。

**当前协议的两个障碍（需突破）**：
1. `pushDirty` 只推 `dirty=1`，已同步条目不会上传
2. 服务端 `base_seq` 乐观锁：空库下条目 `base_seq != 0` 会命中 40903 拒绝

**改动**：

| 层 | 改动 |
|---|---|
| 客户端 syncer | 检测 `server_seq=0 且本地有数据` → 进入"重建模式"，把全部本地条目以 `base_seq=0` 重推 |
| 服务端 push | 增加"重建模式"：接受已有条目的 `base_seq=0` 覆盖；同条目冲突按 `updated_at` LWW（新的覆盖旧的）+ 非删除优先 |
| 客户端 | 重建后重新拉取，校准本地 seq 为新服务端分配值 |

**「谁最新」判定**：`updated_at` 时间戳 LWW + 兜底规则（先保留非删除版本，再比时间戳）。
个人团队规模下时钟漂移危害可控；若要求更严，升级为逻辑版本号（每条目 `version` 字段）。

**边界情况（本阶段主要工作量）**：
- 多客户端并发重建（先后连上空库，谁先谁后）
- 部分数据缺失（某客户端本地不完整）
- 墓碑（deleted）条目的重建
- 重建期间 SSE/seq 的竞态

---

### P0：定时备份脚本（可选，让备机有数据）

**场景**：团队愿意配备份时，让备用服务器始终有准实时数据。

**方案**：主服务器 cron 定时把 `passbook.db`（`sqlite3 .backup` 一致快照）rsync 到备机。

```bash
# 主服务器 crontab，每 10 分钟
*/10 * * * * sqlite3 /data/passbook.db ".backup /tmp/bak.db" && \
             rsync /tmp/bak.db 备机:/data/passbook.db
```

**代价**：切换后最多丢 10 分钟数据。有备份时，P4 的"全量重传"几乎不会触发。

## 五、改动面汇总

| 阶段 | 文件数 | 迁移 | 复杂度 |
|---|---|---|---|
| P1 | 文档 | 0 | 极小 |
| P2 | ~6 | 1（servers 表） | 中 |
| P3 | ~5 | 1（redirect 字段） | 中 |
| P4 | ~6 | 0 | 中偏大（边界多） |
| P0 | 1 脚本 | 0 | 极小 |

**建议排期**：P1+P0（立即，成本极低）→ P2+P3（二期）→ P4（三期）。

---

## 六、风险与待确认

1. **无感 ≠ 零丢失**：切换无感是连接层，数据是否最新取决于备份（P0）。无备份场景下，
   客户端本地就是唯一数据源，重建时以"各客户端本地数据"为准。
2. **自动切换阈值**：需实测"连续失败 N 次"的 N 取值，避免网络抖动误切。
3. **备用地址形式不限**：客户端地址列表的每个条目可以是任意形式——旧域名（穿透已重指向
   新机器）、新域名、或 IP 直连。切换 = 切到列表下一个地址，客户端**不预设"域名重指向"**；
   域名/IP 的变更由团队在穿透服务或 DNS 侧自行配置，客户端只认地址列表，与地址形式解耦。
4. **待确认**：团队是否愿意配定时备份（决定 P0 是否落地、P4 的优先级）。
