## 1. 术语与角色

| 术语 | 含义 |
| --- | --- |
| DEK | Data Encryption Key，数据密钥。每个数据组一把，16 字节随机数，SM4 密钥 |
| KEK | Key Encryption Key，由 keyfile 口令经 PBKDF2-SM3 派生，加密保护本地 SM2 私钥 |
| 信封 / Envelope | DEK 被某成员 SM2 公钥加密后的密文副本，存服务端，仅对应私钥可解 |
| keyfile | 管理员用 keytool 为成员生成的私钥文件（口令保护），是成员唯一需要保管的凭据 |
| keyfile 口令 | 保护 keyfile 私钥的口令，仅成员本人知道；即 v2 中的"主口令" |
| 组 / Group | 数据隔离与授权的最小单位，条目必须属于且只属于一个组 |
| seq | 服务端分配的全局单调递增版本号，同步的唯一依据 |
| key_version (kv) | 组 DEK 的版本号；退出/吊销后递增，客户端据此判断本地 DEK 是否过期 |
| 墓碑 / Tombstone | 条目删除后的占位记录（deleted=true），防止已删数据被其他端回传复活 |
| pending_rekey | 组级标记：存在待完成的重加密（由退出/吊销置位） |
| auto-wrap | 客户端后台自动为组内新成员包裹当前 DEK 信封（入伙） |
| auto-rekey | 客户端后台自动生成新 DEK 并重加密组内全部条目（退出） |
| 管理员 | users.role=admin 的用户，通过独立**管理端**应用（内嵌 keytool）管理成员、组、设备与 rekey 触发；管理端只做元数据操作，无解密特权 |
| 设备 | 一个用户可在多台设备登录，每台设备一个独立 token，可单独禁用 |

## 2. 总体架构

```text
┌─────────┐  密文+信封(TLS1.3)  ┌──────────────────┐
    │ 客户端A │ ◄─────────────────► │                  │
    │ 客户端B │ ◄─────────────────► │  服务端 (Docker)  │
    │ 客户端C │ ◄─────────────────► │  Go + SQLite     │
    └─────────┘                     │  只存密文/信封/   │
      ▲                         │  公钥/版本号/审计 │
      │ 私钥、口令、明文         └──────────────────┘
      │ 永不离开本地                      ▲
    ┌──────────┐  genuser 生成 keyfile   │ admin 一键：
    │ 管理端    │ ◄───────────────────── │  建用户/加组/踢人/吊销
    │(独立客户端│  转交本人（线下通道）      │  触发 rekey/审计查询
    │ 内嵌keytool)│                       │  私钥证明注册设备
    └──────────┘
```

要点：

- 服务端是"哑中转站"：不理解、不解密、不索引内容。

- **keyfile 由 admin 在管理端本机生成并离线转交本人**；私钥除了"生成时在管理端本机、导入后在新人本机"外，不经过服务端，服务端只登记公钥。

- 认证体系（token）与数据加密体系（SM2/DEK）完全隔离。

- **人员协同由客户端自动收敛**：服务端只负责"记状态、断权限、校验集合"，重包裹/重加密逻辑全部在在线成员的客户端后台执行（§7.2）。

### 3.1 库边界（一期架构分层，不可破坏）

```text
internal/crypto  ← 共享底座：加密原语，无网络依赖（server / client/core / keytool / 管理端 均可用）
client/core      ← 客户端核心库：vault + syncer + merge + store（一期主体；UI 只是壳）
client/app       ← 标准 UI 壳：仅 Wails 绑定 + 前端，不实现任何业务逻辑
server           ← 独立二进制：只允许 import internal/crypto 与 internal/model/proto，
                   禁止 import client/core（同步引擎是客户端逻辑，服务端只做状态仲裁）
```

- **对外能力**：`client/core` 的公开 API（`client/core/api`）定义为"语言无关语义接口"——输入输出全部是可序列化结构（JSON），UI 侧不接触密钥类型；第三方 UI（Wails/Fyne/Electron/CLI…）import 后可直接复用加解密、同步、存储全链路。
- **单文件约束**：UI 与 core 在同一 Go module 内以源码方式引用，编译后是单个可执行文件（无外部动态库）；若未来出现非 Go 语言 UI 需求，再为 core 增加 c-shared 壳（导出 JSON 进出 C API），一期不引入 CGO。
- **二期边界**：UI 完善（§14.2）只许动 `client/app/frontend` 与 `client/app/app.go` 的绑定层，`client/core/api` 契约保持不变。

## 4. 加密体系（完整）

### 4.1 密钥层次

```text
keyfile口令(人脑) ──PBKDF2-SM3(salt,100000)──► KEK(16B)
    KEK ──SM4-GCM──► 保护 SM2 私钥（keyfile，仅本人持有）
    SM2 私钥 ──解开自己的信封──► DEK(16B, 每组一把)
    DEK ──SM4-GCM──► 条目密文
    DEK 派生 HMAC 密钥 ──HMAC-SM3──► 条目防伪章
```

与 v2 完全一致，**加密级别不变**。

### 4.2 算法与参数定值

| 用途 | 算法 | 参数 |
| --- | --- | --- |
| 条目加密 | SM4-GCM | key=DEK(16B)，nonce=12B 随机，AAD=长度前缀编码(entry_id 与 group_id) |
| 条目防篡改 | HMAC-SM3 | key = SM3(DEK 拼接 "hmac") 的前 16 字节 |
| DEK 包裹 | SM2 加密 | C1C3C2 模式，曲线 sm2p256v1 |
| 设备注册签名 | SM2 签名 | SM3withSM2，签名内容为服务端下发的 challenge |
| keyfile 派生 | PBKDF2-SM3 | salt=16B 随机，迭代 100000，输出 16B KEK |
| 本地私钥加密 | SM4-GCM | key=KEK，nonce=12B 随机，AAD="passbook-keyfile-v1" |
| 随机数 | crypto/rand | 一律使用密码学安全随机源 |

### 4.3 Wire Format（线上/落盘格式，统一定义）

**条目密文包**（entries.ciphertext 列，JSON 序列化后存 TEXT）：

```json
{
    "v": 1,
    "alg": "SM4-GCM",
    "kv": 1,
    "nonce": "base64(12B)",
    "ct": "base64(...)",
    "hmac": "base64(32B)"
}
```

- `kv` = key_version，加密时使用的 DEK 版本；退出重加密后递增，客户端据此判断本地 DEK 是否过期。

- `hmac` = HMAC-SM3(key_derived, 长度前缀编码(entry_id \| group_id \| kv \| nonce \| ct))。

**密钥信封**（key_envelopes.wrapped_dek 列）：

```json
{ "v": 1, "alg": "SM2-C1C3C2", "data": "base64(...)" }
```

**keyfile**（私钥文件，`xxx.key`，管理员转交本人）：

```json
{
    "v": 1,
    "kdf": { "alg": "PBKDF2-SM3", "salt": "base64(16B)", "iter": 100000 },
    "nonce": "base64(12B)",
    "ct": "base64(SM2私钥DER的密文)"
}
```

### 4.4 密钥生命周期

- **生成（管理端，唯一的密钥生成路径）**：admin 在**管理面板**（client/app 的 --admin 模式；或命令行 `keytool genuser --name zhangsan`）交互式设置 keyfile 口令，输出：

- `zhangsan.key`：SM2 私钥，KEK 加密（KEK 由 keyfile 口令派生）；

- `zhangsan.pub.json`（含 name、sm2_public_key 与 **attestation 注册凭证**的 JSON），用于管理端导入。

- **注册凭证（attestation，确保只有 keytool 生成的密钥能注册）**：keytool 用部署级共享密钥 `PB_REG_SECRET` 计算 `attestation = HMAC-SM3(PB_REG_SECRET, "passbook-attestation-v1" || name || sm2_public_key)` 写入 pub.json；服务端 `POST /admin/users` 导入时校验，**凭证不匹配一律拒收**。外部工具自造的密钥无法通过校验，从技术上封死"绕过 keytool 自行注册"。私钥仍不经过服务端，零知识不变。

- admin 将 keyfile 与口令**分两条安全通道**转交本人（U 盘 / 加密聊天）。服务端全程只见公钥。

- **入伙（auto-wrap，自动收敛）**：admin 一键建用户、加组。任一在线成员的客户端在下一轮同步（SSE 推送 ~1s）检测到"组内存在无信封的 active 成员"，用当前 DEK 为其包裹信封并上传（kv 不变，仅追加，服务端拒绝覆盖已有信封）。新人导入 keyfile 解锁后拉到自己的信封即可解密，全程无手工操作。

- **退出（auto-rekey，自动收敛）**：admin 一键吊销/移出。服务端立即完成**断权**（token 失效、移除组成员、删除该成员全部 kv 信封、置 pending_rekey）。任一在线剩余成员的客户端在下一轮同步自动执行：

1. 用旧 DEK 解出组内全部条目明文；

1. `crypto/rand` 生成新 DEK（kv+1）；

1. 为新 DEK 向**全部 active 成员**包裹信封并先上传（服务端确认集合==active 成员后升 kv、清 pending_rekey）；

1. 用新 DEK 重加密全部条目并 push（kv+1）。

**关键不变量：客户端绝不用低于组当前 kv 的 DEK 加密任何新数据**——重加密完成前，该组新写入在本地挂起。因此被移除者即使保留旧 DEK，也读不到任何离职后的新数据。

- **崩溃恢复**：重加密是"可续跑"的——旧 kv 信封在组内全部条目到达新 kv 前由服务端保留（§6.3），任一成员上线后把 kv 落后于当前 kv 的条目继续重加密并 push，直至收敛。

- **keyfile 口令修改（完整流程，不影响线上数据，但本地 KEK 派生数据必须连带重加密）**：

    口令修改必须在**解锁态**下进行（内存持有旧 KEK 与明文密钥），单事务完成：

    1. 输入旧口令验证 + 新口令二次确认（<12 位强度警告）
    2. 新口令 PBKDF2-SM3 派生**新 KEK**（新 salt）
    3. 用旧 KEK 解密、新 KEK 重加密以下全部本地数据：
       - keyfile 本体（SM2 私钥密文）
       - `device_state.token_enc`（设备 token）
       - `key_cache.dek_enc`（全部组的 DEK 缓存）
       - `local_entries.plaintext_cache_enc` / `base_enc`（明文缓存与冲突快照）
    4. 若已开启 DPAPI 自动解锁 → 用新 KEK 重写 DPAPI 凭据
    5. 任一列重加密失败 → 整体回滚，保持旧口令可用

    - **为什么必须连带重加密**：上述各列均为 KEK 派生密钥加密，派生标签不变、根 KEK 变了则全部解不开
    - 建议改口令前先 push 完未推送修改（清 dirty/base_enc），缩小回滚面
    - 线上数据（服务端密文、信封、token 有效性、组成员关系）完全不受影响——DEK 与私钥本身没变，只是本地保护壳换钥匙

- **keyfile 丢失/口令遗忘（完整找回流程）**：

    1. **admin 生成新密钥**：管理端内嵌 `keytool genuser --name <原用户名>` 生成新 keyfile + pub.json（含新 attestation）
    2. **admin 调用 keyfile-reset**：`POST /admin/users/:uid/keyfile-reset`，请求体携带新 `sm2_public_key` 与新 `attestation`
    3. **服务端校验 attestation**：与 `POST /admin/users` 相同逻辑，校验 `attestation == HMAC-SM3(PB_REG_SECRET, "passbook-attestation-v1" || name || sm2_public_key)`，不匹配 → 40001 拒绝
    4. **服务端单事务执行**：更新 `users.sm2_public_key` + 作废该用户全部设备（`devices.status=disabled`，token 全部失效）+ 删除该用户全部信封（所有 kv）+ 置所在各组 `pending_rekey=1`
    5. **在线成员 auto-wrap**：剩余在线成员下一轮同步检测到 `missing_envelopes` 包含该用户（新公钥无信封）→ auto-wrap 为新公钥包裹当前 DEK 信封（kv 不变，仅追加）
    6. **用户重新注册设备**：导入新 keyfile → 输口令 → 解出 SM2 私钥 → `POST /auth/device-challenge` + `POST /auth/device`（用新私钥签名）→ 获得新 token
    7. **用户拉取数据**：`GET /sync?since=0` → 拉到自己的新信封 → 解出 DEK → 解密全部条目

    - 若该用户所在组同时触发了 rekey（步骤 4 的 pending_rekey），则 auto-rekey 与 auto-wrap 合并执行：先换新 DEK（kv+1），再为新公钥包裹新 kv 信封
    - keyfile-reset 期间该用户无法登录（全部设备已作废），直到导入新 keyfile 完成设备注册

## 5. 数据模型

### 5.1 条目明文结构（客户端，加密前）

**架构原则（v3.x 修订）**：条目明文是**任意 JSON**，由 UI 自由定义；core 与服务端只做「明文 ↔ 密文」的透明管道，**不解析、不校验明文内容**（明文以 `[]byte` 透传，加密/解密/同步/冲突合并均不依赖具体字段名）。下方「project/env/ip_type/acc_type/account 五层 + custom」是 UI 的**可选组织模板**，非强制骨架——UI 可平铺、可跳层、可完全自定义字段；明文格式由 UI 单一权威决定。

树形模型（可选模板）——一条目 = 一个树节点，六类 `type`（五类层级 + 一类万能节点 `custom`）：

```json
{
    "schema_version": 1,
    "type": "project",
    "title": "生产环境",
    "parent_id": null,
    "fields": {},
    "custom_fields": {}
}
```

叶子节点（account 类型）示例：

```json
{
    "schema_version": 1,
    "type": "account",
    "title": "prod-web-01 root",
    "parent_id": "uuid-of-acc_type-parent",
    "fields": {
        "user": "root",
        "password": "...",
        "ip": "10.0.1.10",
        "port": 22,
        "remark": "..."
    },
    "custom_fields": { "机房": "深圳" }
}
```

主体五层任一层旁挂的补充卡片（custom 类型，内容可扩展）示例：

```json
{
    "schema_version": 1,
    "type": "custom",
    "title": "结构信息",
    "parent_id": "uuid-of-ip_type-parent",
    "fields": {},
    "custom_fields": {
        "机房拓扑": "单机柜，主备双链路",
        "负责人": "张三",
        "采购日期": "2026-01-15"
    }
}
```

六类 type 说明：

| type | parent_id 必填 | 说明 | fields 示例 |
| --- | --- | --- | --- |
| `project` | null | 顶层项目节点 | `{}` |
| `env` | project | 环境节点（生产/测试/开发） | `{}` |
| `ip_type` | env | IP 分类节点（如 Web/DB/中间件） | `{}` |
| `acc_type` | ip_type | 账号类型节点（如 OS 账号/数据库账号） | `{}` |
| `account` | acc_type | 叶子节点，实际账号条目 | `{"user":"root","password":"...","ip":"10.0.1.10","port":22,...}` |
| `custom` | project / env / ip_type / acc_type（任一层旁挂） | **万能节点**：挂在主体五层任一层的补充信息卡片（结构信息/说明/配置等，不含账号） | `{}`（内容全走 custom_fields） |

规则：

- `type`（可选模板字段）：可选值 `project / env / ip_type / acc_type / account / custom`，仅当 UI 采用五层模板时才有层级语义；自由模式下 UI 可自定义。**type 创建后不可变更**（改类型 = 删除原节点 + 新建目标类型节点），由 UI 声明为不可变字段（`immutableFields`），不参与冲突合并。
- `parent_id`：指向父节点 entry_id（UUID）；`project` 类型为 `null`。**parent_id 存储在密文明文里，服务端不可见**。
- `title`：各层级节点都有标题，用于树形展示。
- `fields`：仅 `account` 类型有实质内容；其余类型 `fields` 为空对象。
- `custom_fields`：自由扩展区，所有类型均可使用；任意层级允许新增字段。
- **`custom` 万能节点（可选五层模板 + 旁挂补充卡片）**：
  - **五层为可选模板**：project → env → ip_type → acc_type → account 是可选的推荐骨架，**允许跳层、允许自由嵌套**；UI 不强制定层、不强制逐层（层级约束不再由 core 或服务端强制，仅作为 UI 的可选引导）；
  - **挂载位置**：旁挂在 project / env / ip_type / acc_type 任一层之下，想在哪层补散乱信息就在哪层挂；**不能挂在 account 下**（account 是纯叶子）；
  - **用途限定**：只承载**除账号信息外的结构性信息**（机房拓扑、负责人、说明、配置、文档等散乱信息的补充）；
  - 内容全部放在 `custom_fields`（键值自由、可扩展），`fields` 恒为空；
  - **是叶子卡片，不挂任何子节点**——账号信息永远走固定五层的 acc_type→account 路径，不组织到 custom 下；
  - 客户端用**通用动态表单**渲染：扫描 `custom_fields` 自动生成输入控件（文本/多行/数字/密码等），无需固定模板；未知字段遵循"原样保留"铁律；
  - 不参与类型校验——服务端仍不解析明文；五层层级正确性由 UI 自行约束（core 与合并器不校验层级）。
- `parent_id` 变更（移动节点）= 正常编辑该条目并 push。
- 删除非叶子节点 = 递归删除全部子节点（客户端负责生成全部子节点的墓碑 push）。
- **铁律：客户端解析时不认识的字段必须原样保留并写回**（Go 侧用 `json.RawMessage` 兜底未知字段）。
- 单条密文包上限 256KB，超限客户端拒绝保存。
- **schema_version 演进**：当前版本为 1。未来版本升级时（如 schema_version=2 新增字段），旧客户端遇到高于本地版本的条目时：保留 `schema_version` 原值不修改，未知字段用 `json.RawMessage` 原样保留并写回，不阻塞同步与解密。新客户端可读取新字段并按新逻辑处理。版本升级只允许追加字段，不删除/重命名已有字段（前向兼容铁律）。

### 6.3 关键接口定义

**POST /auth/bootstrap**（无认证，仅首次）

```json
请求: {
    "bootstrap_token": "32B 随机(base64url)",
    "name": "admin01",
    "device_name": "admin-pc",
    "sm2_public_key": "base64(DER)"
    }
    响应: { "user_id": "uuid", "device_id": "uuid", "token": "...", "role": "admin", "expires_in": 2592000 }
```

- 校验：users 表为空 且 token 与首启生成值一致（一次性）。

- 单事务：建 admin 用户、建设备、销毁 token。此后本接口永久不可用。

**POST /auth/device-challenge**（无认证）

```json
请求: { "user_id": "uuid" }
    响应: { "challenge": "base64(32B随机)", "expires_in": 300 }
```

- challenge 绑定 user_id，5 分钟过期、一次性（核销与设备注册同事务）。

**POST /auth/device**（无认证）

```json
请求: {
    "user_id": "uuid",
    "device_name": "zhangsan-mbp",
    "challenge": "base64",
    "signature": "base64(SM3withSM2(challenge))"
    }
    响应: { "device_id": "uuid", "token": "base64url(32B)", "expires_in": 2592000 }
```

- 服务端用库中该用户公钥验签；验签通过建设备、发 token。

- **token=32B(256bit) 随机 base64url，库中只存 SM3(token)，token 本体仅此一次返回。**
- `expires_in` = token 有效期秒数（与 `PB_TOKEN_TTL` 对应，默认 2592000 = 30 天）。

**POST /auth/refresh**（需认证）

```json
请求: {}
    响应: { "token": "base64url(32B)", "expires_in": 2592000 }
```

- 请求体为空，靠当前 Bearer token 认证。
- 服务端校验当前 token 有效 → 生成新 token → 旧 token 即刻作废（SM3 哈希替换）→ 返回新 token。
- `expires_in` = token 有效期秒数（与 `PB_TOKEN_TTL` 对应，默认 2592000 = 30 天）。
- 旧 token 作废后，其他使用旧 token 的设备/连接收到 40101。

**POST /auth/heartbeat**（需认证）

```json
请求: { "hostname": "WIN-ABC123" }
    响应: { "ok": true }
```

- 客户端启动/解锁后立即调一次，之后每 30s 调一次。
- 服务端在中间件中更新 `devices.last_ip`（取 socket RemoteAddr）、`devices.last_seen`（当前时间）、`devices.hostname`（请求体上报）。
- 心跳不占用同步接口限流配额（§8.3 限流单独定义）。
- 心跳失败不阻塞客户端主流程（静默重试，失败累计 3 次后标记连接异常）。
- SSE 长连接的 keepalive（15s）与心跳互补：SSE 在线时心跳仍需上报 hostname（SSE 不携带 hostname）。

**GET /users**（需认证）

```json
响应: {
    "users": [
    { "user_id": "uuid", "name": "zhangsan",
      "sm2_public_key": "base64(DER)",
      "status": "active" }
    ]
}
```

- 返回全部 active 用户的 user_id、name、sm2_public_key，供客户端包裹 DEK 信封用。
- 不返回 revoked 用户（服务端永不向认证用户返回 revoked 用户数据）。
- 不含在线状态/设备信息（那是 admin 专用接口 GET /admin/devices 的职责）。

**GET /sync?since=N[&group_id=GID]**（携带 `X-Key-Versions: gid:kv,gid2:kv2` 声明本地信封版本）

```json
响应: {
    "server_seq": 1024,
    "changes": [
    { "entry_id": "uuid", "group_id": "uuid", "seq": 1023, "key_version": 2,
      "ciphertext": "{...}", "deleted": false, "updated_at": 1786300000 }
    ],
    "key_envelopes": [
    { "group_id": "uuid", "key_version": 2, "wrapped_dek": "{...}" }
    ],
    "groups": [
    { "id": "uuid", "name": "G1", "key_version": 2, "pending_rekey": false,
      "archived": false,
      "missing_envelopes": [ "user_uuid" ] }
    ]
    }
```

- 只返回请求者所在组的变更；`since` 之后、按 seq 升序、单次上限 500 条。
- `group_id`（可选）：指定时只返回该组的 changes 与 key_envelopes，`groups` 数组也只含该组；**指定时校验请求者为该组成员，否则 40302**（不指定时按所在组隐式过滤，无此问题）；不指定时返回用户所有所在组的变更（原行为不变）。
- `since=0 & group_id=GID` 语义 = 拉取该组从最初到现在的全量变更，用于新加入组的初始化。

- `key_envelopes` 只含 `user_id=自己` 且比 `X-Key-Versions` 声明更新的信封。

- **`groups` 携带关键协同状态**：

- `pending_rekey=true` → 该组有待完成重加密，客户端进入 auto-rekey；

- `missing_envelopes` = 该组当前 kv 下**没有信封的 active 成员** → 客户端进入 auto-wrap。

**POST /sync/push**

```json
请求: {
    "mutations": [
    { "entry_id": "uuid", "group_id": "uuid", "base_seq": 100,
      "key_version": 2, "ciphertext": "{...}", "deleted": false }
    ]
    }
    响应: {
    "results": [
    { "entry_id": "uuid", "ok": true, "new_seq": 1024 },
    { "entry_id": "uuid2", "ok": false, "error": 40901,
      "current": { "seq": 1010, "ciphertext": "{...}", "key_version": 2 } }
    ]
    }
```

校验链（顺序固定，改动需评审）：token 有效 → 用户 active → 用户属于该 group → 组未归档（archived=1 拒收 40905）→ ciphertext ≤ 256KB → **key_version == 组当前 kv**（旧 kv 拒收，40902，提示先重加密）→ base_seq 等于该条目当前 seq（新增条目 base_seq=0 且 id 不存在）→ 事务内分配 seq 写入。

**POST /groups/:gid/keys**（信封集合提交：入伙 / rekey）

```json
请求: {
    "key_version": 3,
    "envelopes": [ { "user_id": "uuid", "wrapped_dek": "{...}" } ]
    }
```

校验：

- 请求者是该组成员；

- **组未归档**（archived=1 拒收 40905——归档组冻结协同，杜绝归档期间 kv 被推进导致 rekey 卡死）；

- `key_version` == 组当前 kv（**入伙追加**：只允许为 `missing_envelopes` 中的成员新增，不允许覆盖已有信封）或 == 当前 kv+1（**rekey 替换**：集合必须恰好等于全部 active 成员）；

- envelopes 的 user 集合必须是 active 成员的子集。

成功后的状态变更：

- 入伙（kv 不变）：仅追加新信封。

- rekey（kv+1）：`groups.key_version` 升为 kv+1；**若组内全部条目已到达新 kv 则清 pending_rekey**。

- **旧 kv 信封保留规则（崩溃安全关键）**：只要该组存在 key_version 落后于组当前 kv 的条目，旧 kv 信封就保留（供成员恢复重加密）；在 push 事务内检测到全部条目已到达当前 kv 时，同一事务删除全部旧 kv 信封。**"全部条目到达当前 kv"的判定排除 deleted=true 的墓碑**（墓碑密文为空、不参与重加密，见 §7.4）。

- 被吊销/移出成员的信封在 revoke/remove 时已删除（所有 kv），不在此列。

**POST /admin/groups/:gid/rekey**（admin，预防性重加密触发）

```json

```

- 语义：**触发不等于执行**。服务端仅将该组 `pending_rekey` 置 1（若已是 1 则幂等返回当前状态），随后由**在线成员客户端**按 §7.2 auto-rekey 流程生成新 DEK（kv+1）并重加密收敛；全员离线时保持置位，任一成员上线后自动执行。**归档组允许置位（挂起），执行冻结至 unarchive 后收敛**（§6.3 归档语义）。
- 用途：怀疑 DEK 泄露、定期轮换等**预防性换钥**场景（revoke/remove 触发的是自动置位，不需要此接口）。
- 管理端进度可见：管理端查询 `GET /admin/groups`（只返回元数据，**不含任何密文/信封**）观察该组 `pending_rekey` 何时清除、`key_version` 是否递增，即视为重加密收敛完成。

**POST /admin/groups/:gid/unarchive**（admin，重启组）

```json
请求: {}
    响应: { "group_id": "uuid", "archived": false }
```

- **归档**：需输入组名二次确认（与吊销操作一致的安全规范）。
- **幂等**：对已归档组再 archive、对未归档组 unarchive → 幂等返回当前状态（`archived: true/false`），不报错（与 rekey 置位幂等风格一致）。
- **归档完整语义：协作冻结 + 数据只读 + 可逆 + 不断权**：
  - **冻结（不产生新变更、不执行协同）**：
    - `POST /sync/push` 拒收（40905）；`POST /groups/:gid/keys` 拒收（40905）——push 与信封提交双拒收，杜绝归档期间 kv 被推进导致 rekey 卡死
    - SSE 不再推送该组变更（无新 seq 产生的自然结果 + 防御性规则）
    - `GET /sync` 的 `groups` 数组中该组标记 `archived: true`；归档组**不产生 `missing_envelopes`**（即使期间新加成员）
    - 客户端对归档组的处理：changes / envelopes **正常入库**（冻结期无新变更，进来的都是历史，新设备凭信封解密后只读查看）；跳过的是协同动作与写操作：auto-wrap / auto-rekey 不执行、本地禁止编辑该组条目（UI 只读、不产生 dirty）（§7.2 4d）
  - **只读（历史与信封照常可取）**：
    - 归档组**不再产生新变更**（push 被拒的自然结果），但**历史 changes 仍可正常拉取**（`since=0&group_id=<gid>` 可拉全量历史，新设备/换机可查看归档内容）
    - `GET /keys/mine` 照常返回该组信封（新设备凭信封可解密历史）
    - 成员关系、信封、条目密文全部保留，不删除
    - 成员已解密的本地缓存仍可查看
  - **可逆（unarchive 收敛）**：清除 `archived` 标记；客户端检测到 archived 翻转（true→false）→ 对该组全量拉取（`since=0&group_id=<gid>`，与新加入组同一机制，§7.2 4d）；归档期间挂起的状态（pending_rekey、missing_envelopes）按正常 auto-rekey / auto-wrap 流程收敛。若归档期间组 DEK 未变（无成员变动），成员可直接解密。
  - **不断权（身份/权限操作即时生效）**：归档期间 revoke / remove / keyfile-reset 照常有——
    - **revoke/remove**：断权单事务即时生效（token 失效 + 移除成员 + 删信封 + 置 pending_rekey），不依赖同步；安全链完整：被移除者拿旧 DEK 只能读归档前旧数据（其本就持有），归档期间无新数据产生（冻结），unarchive 后 rekey 先收敛、写挂起保证旧 DEK 写不出新数据——无泄露窗口
    - **keyfile-reset**：换绑公钥 + 作废全部设备即时生效；新公钥信封因 auto-wrap 冻结**暂不产生**，该用户在 unarchive 并完成设备注册前看不到数据，unarchive 后 auto-wrap 补齐、全量拉取，数据不丢
    - **新增成员**：成员关系立即建立，但无信封（auto-wrap 冻结），unarchive 前看不到数据；unarchive 后 auto-wrap 补齐、本人全量拉取历史即可正常使用
  - 管理端对上述归档期操作须展示后果提示文案（§9.3）。
- 审计日志记录 `archive` / `unarchive` action。

### 6.4 服务端硬规则

1. 任何接口不接收、不记录明文敏感字段；日志只记元数据。

1. 所有多表写操作包事务；seq 分配与条目写入同一事务。

1. 服务端**永不主动返回** revoked 用户任何数据（信封、组成员关系即刻对其关闭）。

1. 管理接口不赋予内容特权：admin 能吊销人、移出组、禁用设备，但拿到的仍是密文；删除条目一律走墓碑语义（客户端 push deleted=true），**不提供服务端"物理删行"接口**。

1. **断权即时性**：revoke/remove 单事务完成"token 失效 + 移除成员 + 删该成员信封 + 置 pending_rekey"，服务端不依赖任何成员在线即可完成断权。

1. **信封集合校验严格**：rekey 集合必须==全部 active 成员；入伙只允许追加；任何误删/越权包裹被拒（40904）。

1. 服务端不参与加解密：不持有、不接触 DEK 与明文，auto-wrap/auto-rekey 只是客户端行为，服务端仅做状态与集合校验。

1. **推送只通知不送数据**：push/信封提交成功后，服务端经 `/sync/stream` 通知相关组订阅者；通知仅含 seq 元数据与组 ID，绝不携带密文/信封；通知丢失不影响收敛（客户端以拉取为准，断线回退轮询）。

## 7. 同步协议（完整）

### 7.1 时钟与版本

- 唯一权威时钟是服务端 `seq_counter`，客户端时钟不参与任何判定。

- seq 分配：`UPDATE seq_counter SET value=value+1 ... RETURNING value`，与条目写入同事务。

- 客户端本地持久化 `last_seq`（每设备一份）。

### 7.2 同步循环（客户端 syncer 执行，含无感协同）

```text
0. 启动/解锁：立即连接 /sync/stream 订阅变更（断线自动重连 1s→2s→…→30s 封顶），并**立即执行一次增量拉取**（since=last_seq）补齐离线期间变更
1. pull: GET /sync?since=<last_seq>（携带 X-Key-Versions）
    2. 处理 key_envelopes（**先于 changes**）：用私钥解出新 DEK，替换内存与本地加密缓存
    —— rekey 批次与新成员首次同步的密文都依赖新 DEK，信封必须先落地
    3. 处理 groups（无感协同核心）:
    a. auto-wrap（含冷启动）：对任一组 missing_envelopes 中的成员，用当前 DEK 包裹
      → POST /groups/:gid/keys（kv 不变，仅追加）
      ——成员公钥经 GET /users 获取并本地缓存，检测到 missing_envelopes 变化时刷新；
      **冷启动分支**：组内当前 kv 下无任何信封（新建组还没有 DEK）→ 首个检测到
      该状态的在线成员 crypto/rand 生成 DEK（kv=1），为全部 active 成员包裹并上传
      ——kv=1 == 组当前 kv，走 keys 校验的**入伙追加分支**（此时服务端算出的
      missing_envelopes == 全部 active 成员，提交全集恰好合法）；
      多人同时冷启动各自生成不同 DEK → 信封层仲裁（不允许覆盖已有信封，
      先到者生效，后到者 40904 重拉收敛，同 §7.6）
    b. auto-rekey：若某组 pending_rekey=true 且本地持有该组旧 kv 信封
      → 执行重加密（见下）
    c. 新加入的组（group_state 无该组记录）→ 对该组执行一次全量拉取（GET /sync?since=0&group_id=<gid>），
      避免因全局游标过高而漏掉该组历史条目
    d. archived=true 的组（协作冻结）→ changes / envelopes **正常入库**
      （冻结期无新变更，进来的都是历史；新设备凭信封解密后只读查看）；
      跳过的是协同动作与写操作：auto-wrap / auto-rekey 不执行，
      本地禁止编辑该组条目（UI 标记"已归档（只读）"，不产生 dirty）；
      归档期间 groups 数组仍返回该组（含 archived 标记），
      客户端在 group_state 记录各组 archived 状态；
      检测到某组 archived 从 true 翻转为 false（unarchive）→ 立即对该组执行全量拉取
      （GET /sync?since=0&group_id=<gid>），与新加入组同一机制；
      归档期间挂起的 pending_rekey / missing_envelopes 在恢复后按正常 auto-rekey / auto-wrap 收敛
    4. 逐条处理 changes:
    a. 本地无该组该 kv 的 DEK（信封尚未到达，如 auto-wrap 完成前/归档冻结期新成员）
      → 密文原样写入 pending_entries 暂存（"等待信封"），**不做 hmac 校验、不进 bad_seq**；
      信封到达（步骤 2 解出新 DEK）后补验 hmac + 解密入库并清除暂存；
      暂存期间同 entry_id 来了更新版（新 seq）→ 覆盖暂存（保留最新密文）；
      暂存期间该条目来了墓碑 → 清除暂存（条目已删，无需再等信封）
    b. 有 DEK 时校验 hmac（用本地该组对应 kv 的 DEK）
    c. 解密失败或 hmac 不符 → **密文仍写入 local_entries**（ciphertext 落库、
      plaintext_cache_enc 为空、UI 不展示），同时记入 bad_seq 跳过清单（fail_count=1）；
      后续每轮同步循环从**本地库**取出该密文重试解密（fail_count 递增；
      重试间隔 = 下次同步循环，即 SSE 触发或轮询周期 5s/30s），避免单条脏数据永久阻塞；
      连续 5 次仍失败的条目写入本地告警日志并在 UI 标记"该条目同步异常"，不再自动重试，需用户手动处理（查看详情或删除重建）
    d. deleted=true → 本地删除该条目（保留 30 天本地回收站）
    e. 正常条目 → 解密入库；若本地存在"未推送的本地修改" → 转入冲突副本
    5. push: 收集本地脏条目，批量 POST /sync/push
    - 加密统一使用组当前 kv 的 DEK；若本地 DEK 落后（40902）→ 先拉新信封 → 重加密 → 重推
    - ok → 清脏标记，记录 new_seq
    - 40901 冲突 → 保留本地版为"冲突副本"，以服务端版为当前版
    6. last_seq = server_seq（**pending_entries 暂存不影响 last_seq 推进**——密文已落本地，
      信封到达后从暂存补处理，无需重新拉取），等待触发源：SSE 推送事件（收到 change 立即再拉）/ 本地变更事件 / 手动刷新
    - SSE 不可用时回退轮询：网络健康 5s、降级/失败 30s + 指数退避（1→2→4→8→16→30s 封顶）；连续失败 10 次后切换为轮询模式（30s 间隔 + 每 5 分钟尝试恢复 SSE）；恢复 SSE 后执行一次增量拉取并回到推送驱动
```

**auto-rekey 完整流程（组级、崩溃可续）**：

```text
触发：pull 看到 pending_rekey=true 且本地有旧 kv 信封；或 push 收到 40902；
    或管理端经 POST /admin/groups/:gid/rekey 手动触发（预防性换钥，§6.3）。
    1. 本地挂起该组的所有新写入（UI 显示"组密钥升级中"，非阻塞提示）
    2. 用旧 DEK 解密组内全部 kv<新版本 的条目明文（内存中）
    3. crypto/rand 生成新 DEK（kv+1）
    4. 向全部 active 成员包裹新 DEK 信封 → POST /groups/:gid/keys（kv+1 集合）
    - 成功：服务端升 kv、可能清 pending_rekey（若条目已全部到达）
    - 40904/40902 失败：另一成员已先完成 → 重拉后收敛，本方退出
    5. 用新 DEK 重加密全部条目（kv+1）→ 批量 push
    6. 解除本组写挂起；后续新写入使用新 DEK
```

**写挂起不变量**：客户端**绝不用低于组当前 kv 的 DEK 加密任何新数据**。重加密完成前，该组新写入只进本地队列，不出网。因此即便全员离线，也不会产生"用旧 DEK 加密的新数据"外流。

### 7.3 冲突规则

**冲突处理（参考 Git 三路合并，字段级；由独立通用 JSON 合并器实现）**：

合并由 `internal/merge` 独立模块完成（纯函数、零业务依赖），对任意 JSON 结构做**递归三路合并**，不依赖五层模板或具体字段名（如 title/parent_id/fields 均不硬编码）。core 在收到 40901 冲突时调用它；UI 也可复用同一模块。

- **判定**：push 时 `base_seq != 服务端当前 seq`（40901），响应携带服务端当前版（theirs）。

- **三路输入**（合并算法为纯函数，无副作用）：
  - `base` = 共同祖先：**首次编辑前自动保存的明文快照**（`local_entries.base_enc`，KEK 派生密钥加密）。写入与清除时机如下：
    - **写入**：条目进入编辑状态时，若 `base_enc` 为空则写入当前明文快照（首次编辑前快照）
    - **不覆盖**：若 `base_enc` 已存在（尚未 push 成功），后续再次编辑同一条目不覆盖 `base_enc`，保留的是"自上次 push 成功后的第一次编辑前"快照
    - **清除**：push 成功（`ok=true`）后清除 `base_enc`；push 返回 40901 冲突时**保留** `base_enc`，用于三路合并
    - **墓碑冲突**：条目被远端删除（pull 到墓碑）时，`base_enc` 随本地条目转入冲突副本，仍可用于"还原为新条目"操作
  - `ours` = 本地修改版（冲突副本）；`theirs` = 服务端当前版（40901 响应解密所得）。

- **自动合并规则（逐字段，递归）**：对明文 JSON 的**任意嵌套字段**递归做三路合并（不限定 title/parent_id/fields 等具体字段名；嵌套对象递归合并，标量/数组整体比较）——
  - 仅一方改 → 采用改方；
  - 两方都没改 → 保留原值；
  - **两方都改且值不同 → 冲突**：该字段标 Git 式标记，其余字段正常合并（**不做整条二选一**）。
  - 任意字段同规则（title 重命名、parent_id 移动等同样标冲突、进冲突解决页）；**不可变字段**（如 `type`）由 UI 通过 `immutableFields` 声明，合并器校验其不被变更、不参与合并。
  - 数组值字段（如 fields 中的列表型自定义字段）：按"整体替换 + 冲突标记"处理（不做行级拼接，避免语义错乱）。

- **合并结果**：
  - 无冲突字段 → 合并结果直接作为新版本 push（一次成功）；
  - 有冲突字段 → 进入**冲突解决页**：三栏 diff（base / ours / theirs）+ 每字段「采用本地 / 采用服务端 / 手动编辑」，解决后 push 一次。

- **重加密期间的说明**：若某离线成员在重加密期间有未推送修改，恢复后这些修改可能以冲突副本呈现（服务端条目已被重加密版本覆盖），同样走三路合并（base 为本地快照、theirs 为重加密版本），由本人确认；这是 DEK 轮换的固有代价，不丢数据。

- **墓碑 vs 本地修改**：本地存在未推送修改的条目被其他端删除（pull 到墓碑）时，本地版同样转冲突副本并提示"他端已删除此条"，用户可选**丢弃**或**还原为新条目**（生成新 entry_id 重新发布，避免与墓碑 40903 冲突）。

- **服务端零改动**：三路合并全部在客户端完成（base 本地保存、theirs 来自 40901 响应），服务端仍只存一份最新密文。

### 7.4 删除与墓碑

- 删除 = push 一条 `deleted=true`、密文包置空的壳记录（分配新 seq）。

- 其他端 pull 到墓碑后本地删除（留 30 天回收站，纯本地行为）。

- 服务端定时任务每天 **03:00 UTC** 清理 updated_at 早于 90 天的墓碑（物理删除）；清理在单个事务中执行，不影响正常同步。容器时区默认 UTC（§12.2 不引入时区配置，03:00 UTC = 北京时间 11:00，业务低谷期）。

- **离线超 90 天的客户端**：墓碑被清理后，该端回传旧条目时 id 存在性校验将拒绝（40903），不会复活已删数据。

- **墓碑与重加密**：墓碑密文为空、无内容可泄露，**不参与 auto-rekey**（不重加密、不更新 kv）；服务端"全部条目到达当前 kv"的收尾判定**明确排除 deleted=true 条目**，否则历史删除会卡住 pending_rekey 永不收敛（§6.3/§7.2）。

- **墓碑与本地修改**：本地存在未推送修改的条目被其他端删除时，转冲突副本并提示（§7.3 墓碑规则）。

### 7.5 一致性边界

- 单条目原子；多条目批量 push 不保证全成功（逐条返回结果），客户端按结果收敛。

- 客户端断网期间的所有修改在本地排队，恢复后按序 push，冲突按 7.3 处理。

- 重加密/重包裹是幂等收敛的：以服务端 kv 与信封集合校验为准，多客户端竞争时后者自动退出。

- **推送只是通知**：SSE 仅告知"有新 seq"，不保证送达顺序；数据一律以加密拉取为准，SSE 断线自动回退轮询，最终收敛（好网络下变更在 1s 内可见）。

### 7.6 多人并发重加密的仲裁（为什么"不会冲突"）

同一组有多个成员在线时，理论上都会检测到 `pending_rekey` 并各自生成一个"新 DEK"。系统用三层机制保证**最终只收敛到一个 DEK、且不丢数据**：

1. **信封层（服务端仲裁，只有一个新 DEK 生效）**：`POST /groups/:gid/keys` 校验 `kv+1` 时**信封集合必须恰好等于全部 active 成员**，且**不允许覆盖已有信封**。第一个提交成功的成员把组 kv 升到 K+1；其余成员再提交同一 kv+1 信封会被拒（40904），重拉后拿到新信封，收敛到同一个 DEK'。
2. **条目层（乐观锁，不丢数据）**：多人同时重加密 push 同一条目时以 `base_seq` 判定——先推者成功并分配新 seq，后推者收到 40901 后重拉、发现已是 kv+1 新版本、丢弃自己的副本。因两者是同一明文 + 同一 DEK'，内容相同，不构成真分叉。
3. **收尾（服务端事务内判定，不依赖具体成员）**：push 事务内检测到"该组全部条目已到达当前 kv"时，同一事务清 `pending_rekey` 并物理删除旧 kv 信封；谁把最后一条推到位谁触发收尾，天然收敛。

**兜底防线**：push 校验链要求 `key_version == 组当前 kv`（旧 kv 一律 40902 拒收）——任何成员即使绕过客户端"写挂起"，也**无法用旧 DEK 产生新数据**，服务端校验是最终保证。

**边角情况**：

- 离线成员：上线后自动拉 kv+1 信封，本地脏条目用新 DEK 重加密再推；旧 kv 信封在其完成前保留。
- 崩溃续跑：旧 kv 信封保留至全部条目换新；任一成员上线续跑，按 (entry_id, key_version) 幂等，不重复不丢。
- rekey 途中加人/移人：active 成员集合变化 → 信封集合校验不匹配 → 提交被拒 → 重拉后按新成员集合重新 rekey。

**可选优化（非必须）**：服务端可给组加 `rekey_by` / `rekey_locked` 标记，让第一个进入 rekey 的成员成为"主导者"，其余成员只跟随推送重加密条目，避免多人在线时的重复劳动；正确性已由上述三层机制保证。

## 8. 认证与设备管理（完整）

### 8.1 信任链

```text
首启: admin 本机 keytool genuser → 用首启 token 调 /auth/bootstrap → 建立首个 admin
    建用户: admin keytool genuser 生成新人 keyfile → 管理端导入公钥建用户
    → admin 把 keyfile + 口令分两条安全通道转交本人
    加组: admin 一键加组 → 在线成员客户端 auto-wrap 包裹 DEK → 新人拉到信封即可解密
    设备注册: 新人导入 keyfile → 客户端取设备挑战 → 私钥签名 → 服务端验签发 token
    此后: 所有请求 Bearer token；token 泄露 ≠ 数据泄露（只得密文）
```

**keyfile 即身份**：持有 keyfile 私钥即可注册该用户的新设备。因此 keyfile 必须妥善保管，转交走线下安全通道。

### 8.2 规则

- **token**：32B(256bit) 随机，base64url；库中只存 SM3 哈希；有效期 30 天，`/auth/refresh` 滑动续期；连续 10 次认证失败锁定该 IP 10 分钟。

- **设备**：一人多设备各自持 token；丢设备 → admin 或本人禁用该 device，不影响其他设备。

- **在线判定**：设备有活跃 SSE 连接（心跳 15s 内）即在线；无 SSE 时 `last_seen` 在 60s 阈值内也算在线。服务端内存维护活跃连接表，管理端据此展示（§6.3）。

- **IP 与机器名**：设备注册与每次带 token 的请求由中间件更新 `devices.last_ip`、`last_seen`；客户端注册/心跳上报 `os.Hostname()` 存 `devices.hostname`。客户端通过 `POST /auth/heartbeat` 每 30s 上报 hostname 并维持在线状态（离线阈值 last_seen 60s，容忍一次心跳失败）；SSE keepalive（15s）用于维持长连接与活跃连接表，两者互补。均为元数据，服务端可见但零知识不受影响。

- **吊销用户**：全部设备 token 即刻失效、信封删除、从所有组移除（group_members 删除 + pending_rekey 置位，配合 auto-rekey 收敛）。

- **移出组**：该组信封删除、pending_rekey 置位；用户在组外无法再拉取/推送该组数据（40302）。

### 8.3 传输安全

- TLS 1.3；证书二选一：正规 CA 证书，或自签 CA + 客户端内置 CA 指纹固定（pinning，推荐内网/小团队场景）。

- 响应头：`Strict-Transport-Security`、`X-Content-Type-Options: nosniff`、`Cache-Control: no-store`。

- 限流策略（超限返回 429 / 42901）：

| 类别 | 限流规则 | 说明 |
| --- | --- | --- |
| 认证接口 | 5 次/min/IP | /auth/bootstrap、/auth/device-challenge、/auth/device |
| 同步接口 | 120 次/min/token | /sync、/sync/push、/groups/:gid/keys、/keys/mine（含启动拉取与回退轮询；SSE 推送不占配额） |
| 心跳接口 | 30 次/min/token | /auth/heartbeat（30s 间隔 + 抖动余量） |
| Admin 接口 | 30 次/min/token | /admin/* 全部接口 |
| SSE 长连接 | 每 token 最多 4 条 | /sync/stream 并发连接上限 |
| 认证防暴破 | 连续 10 次失败锁 IP 10 分钟 | /auth/* 认证失败（401xx）累计计数，独立于频率限流 |

- Admin 限流独立于同步限流：管理操作频率低但不可被同步洪流挤占（如批量加人时同步限流已满，admin 仍可操作）。
- Admin 限流按 token 而非 IP：admin 通常在固定网络环境，按 token 更精确。
- 心跳限流独立：防止客户端 bug 导致心跳风暴。
- 认证防暴破按 IP：防"低频暴力枚举/撞库"，与 5/min 频率限流叠加生效（频率限流挡洪流，防暴破挡慢速试探）。

**SSE 重连防护**：

- **客户端侧**（§7.2 已有指数退避 1s→2s→…→30s 封顶）：首次断线 1s 后重连，每次失败翻倍退避（1→2→4→8→16→30s），30s 封顶；连续失败 10 次后切换为轮询模式（30s 间隔），每 5 分钟尝试一次恢复 SSE。
- **服务端侧**：同一 token 的 SSE 连接在断开后 2 秒内不允许重新建立（防止抖动风暴）；违反返回 42901 并提示 `Retry-After: 2`。此限制与"每 token 最多 4 条并发"叠加生效。
- **恢复检测**：轮询模式下，客户端每 5 分钟尝试建立一次 SSE 连接；成功后立即切换回推送驱动模式，并执行一次增量拉取补齐轮询期间的变更。

## 9. 客户端设计

> **客户端开发约定**（UI 壳 / 树形数据组织 / 本地编辑 / 变更应用策略 / 辅助功能 / 二期边界）：独立成文，见 `docs/客户端开发约定.md`。加解密见 §4，同步引擎见 §7。

### 9.1 骨架相关部分（完整）

**首启与 keyfile 导入**：

- 新成员首次启动 → 导入 `xxx.key`（admin 转交）→ 输入 keyfile 口令 → PBKDF2-SM3 派生 KEK → SM4-GCM 解出 SM2 私钥（驻留内存，锁定时清零）。
- **keyfile 导出/备份**：导出 = keyfile 文件副本（§4.3 格式，KEK 加密的私钥，口令保护不变）；可选"以新口令导出"（先按 §4.4 流程派生临时 KEK 重加密后导出，原 keyfile 不受影响）。**导出操作强制手输口令**（即使已开 DPAPI 自动解锁），导出文件权限 0600，并提示用户妥善保管/及时删除。

**设备注册**：

- 无设备 token 时：取设备挑战（`/auth/device-challenge`）→ 私钥签名 → `/auth/device` 注册设备 → 得到 token（加密存储，建议 OS 密钥环或 KEK 派生加密）。注册时上报 `device_name`（用户填写）与 `hostname`（`os.Hostname()`，机器名，供管理端展示）。

**解锁流程（vault）**：

```text
启动 → 读 keyfile → 输口令(或自动解锁取 KEK) → 派生/取回 KEK → 解出 SM2 私钥(内存)
    → 若无设备 token 先注册设备
    → GET /keys/mine 拉取我的信封 → 私钥逐个解出各组 DEK
    → DEK 按 {group_id: {key_version, dek}} 缓存于内存，不落盘明文
```

**条目加解密（vault）**：

- 加密：明文 JSON → UTF-8 字节 → 随机 12B nonce → SM4-GCM(DEK, nonce, AAD=长度前缀编码(entry_id|group_id)) → 计算 HMAC-SM3 → 组装 4.3 密文包。

- 解密：解析密文包 → 按 kv 找 DEK（kv 落后则先拉新信封；同步循环中信封先于密文处理，§7.2）→ 验 HMAC（失败则告警拒绝并记 bad_seq，**密文仍落 local_entries、后续从本地重试**；无 DEK 的条目暂存 pending_entries，不验不收）→ GCM 解密 → JSON 解析（未知字段 RawMessage 保留）。

**同步引擎（syncer）**：完整状态机见 7.2。触发源：SSE 推送事件（有新 seq 立即拉取）、本地变更事件、启动自动拉取、手动刷新；SSE 不可用时回退轮询（健康 5s / 降级 30s + 指数退避）。同一时刻只允许一轮同步（互斥锁）。内含 auto-wrap / auto-rekey / 写挂起。

**本地存储**（SQLite）：

```text
local_entries(entry_id, group_id, seq, key_version, ciphertext, plaintext_cache_enc,
              base_enc, dirty, conflict_of, updated_at)
    -- base_enc: 编辑前的"共同祖先"明文快照（KEK 派生密钥加密），供冲突三路合并（§7.3）
    -- plaintext_cache_enc: 解锁态缓存已解密的条目明文（KEK 派生密钥加密），见下方详解
    sync_state(id=1, last_seq, last_pull_at)
    group_state(group_id PRIMARY KEY, archived, initialized_at)
    -- 客户端本地组状态：archived 供 §7.2 4d 翻转检测（unarchive 触发全量拉取）；
    --   initialized_at 记录全量拉取完成时间，无记录即"新加入的组"（§7.2 4c）
    pending_entries(entry_id PRIMARY KEY, group_id, seq, key_version, ciphertext, updated_at)
    -- 等待信封的暂存密文：本地无对应 kv DEK 时原样暂存（§7.2 4a），
    --   不做 hmac 校验、不进 bad_seq；信封到达后补验 hmac + 解密入库并删除暂存行
    key_cache(group_id, key_version, dek_enc)   -- dek_enc 用 KEK 加密
    recycle_bin(entry_id, ciphertext, deleted_at)
    device_state(id=1, device_id, token_enc, expires_at)
    -- token_enc: token 加密存储；expires_at: 注册/刷新时由 expires_in 计算（unix 秒），
    --   供 Token 管理策略做临期刷新判定（见下）
    bad_seq(seq INTEGER PRIMARY KEY, fail_count INTEGER NOT NULL DEFAULT 1)
    -- 坏密文跳过清单；fail_count 持久化连续失败次数，
    --   供"连续 5 次失败"重试/告警判定（§7.2 2b），客户端重启不丢
```

- 敏感列列级 SM4-GCM 加密（KEK 派生密钥）。

- **`plaintext_cache_enc` 详解**：
  - **用途**：解锁态下缓存已解密的条目明文，避免反复执行 SM4-GCM 解密 + JSON 反序列化。树形浏览、搜索、列表渲染时直接读取缓存，提升响应速度。
  - **写入时机**：条目首次被解密时（pull 入库或用户查看触发解密），将明文 JSON 用 KEK 派生密钥（`SM3(KEK || "plaintext-cache")` 前 16 字节）SM4-GCM 加密后写入此列。
  - **读取时机**：解锁态下树形浏览/搜索/列表渲染时，优先读 `plaintext_cache_enc` 解密使用；锁定时不清除此列（仍加密保存），但内存中不保留解密结果。
  - **加密密钥**：KEK 派生密钥（`SM3(KEK || "plaintext-cache")` 前 16 字节），与 `base_enc` 使用不同的派生标签，密钥隔离。
  - **失效与更新**：条目被重新加密 push 后（dirty 清除、新 seq 写入），`plaintext_cache_enc` 同步更新为新明文缓存；pull 到远端更新覆盖本地时，旧缓存作废并按需重新解密写入。
  - **安全边界**：此列是加密的（KEK 派生密钥），锁定后无法解密；攻击者拿到本地数据库文件但无 KEK（即无 keyfile 口令）时，此列与 `ciphertext` 一样不可解密。
  - **可选关闭**：若后续引入 SQLCipher 整库加密（§9.1 搜索章节提到的可选升级），可关闭此缓存以简化实现，直接在内存中维护解密结果。

**Token 管理策略（客户端）**：

- **存储**：device token 用 KEK 派生密钥（`SM3(KEK || "device-token")` 前 16 字节）SM4-GCM 加密后存 `device_state.token_enc`，与 `plaintext_cache_enc` / `base_enc` 使用不同派生标签，密钥隔离。
- **刷新时机**：
  - 客户端维护 token 的 `expires_at`（注册/刷新时由 `expires_in` 计算）
  - 每次 HTTP 请求前检查：距 `expires_at` 不足 24 小时 → 先调 `POST /auth/refresh` 获取新 token，再执行原请求
  - 启动/解锁后立即检查一次（避免启动后 token 很快过期）
- **refresh 失败处理**：
  - 40101（token 已失效）→ 清除本地 token，提示用户重新解锁（可能需要重新注册设备，如 keyfile-reset 后）
  - 网络错误 → 静默重试 3 次（指数退避 1s/2s/4s），仍失败则继续使用当前 token 直到过期或下次成功
  - refresh 成功后立即更新 `device_state.token_enc` 与内存中的 `expires_at`
- **并发 refresh 防抖**：syncer 与 UI 可能同时触发 refresh，客户端用互斥锁保证同一时刻只有一次 refresh 请求，其余等待结果复用
- **过期后行为**：token 过期后所有请求返回 40101，客户端清除本地 token 并提示"会话已过期，请重新解锁"

- **搜索**：默认"解锁后内存搜索"——解密 title/fields 到内存检索，**custom 节点的 title 与 custom_fields 键值同样纳入检索**（散乱结构信息可搜），锁定时清零，**不落盘 FTS 明文索引**（保持本地零知识姿态）；若后续引入 SQLCipher 整库加密，可作为可选升级以支持持久 FTS5 索引。

- 剪贴板复制密码 30 秒后自动清空。

- **密码生成器**：客户端内置随机密码生成（`crypto/rand`），可配置长度（默认 16 位）、字符集（大写/小写/数字/符号）与是否排除易混字符；条目编辑页一键生成并填入，生成的密码仅出现在本地，永不落盘明文、永不出网。

- **自动锁定**：客户端窗口失去焦点（最小化/切后台/非置顶）连续 **5 分钟**无交互 → 自动锁屏并 Wipe 内存密钥（私钥/DEK/KEK）。解锁方式按策略三选一（可配置）：keyfile 口令、Windows Hello 生物识别（三期 3.9）、或**自动解锁**（见下）。
  - **锁定态的同步行为**：SSE 长连接与心跳**保持**（在线状态连续，管理端所见即真实——设备在线只是本地锁了）；**syncer 挂起**（不 pull 不 push，锁定期间不进 pending_entries——那是"信封未到"专用语义）；**解锁后**密钥恢复，复用启动流程"立即增量拉取（since=last_seq）"——`last_seq` 锁定期间未动，期间变更自然一批拉齐，无需特殊处理。

- **自动解锁（可选，Windows 专属）**：解锁后用户可开启"自动解锁"——客户端把派生出的 **KEK 写入 Windows DPAPI**（用户级，默认经 TPM 保护；读取失败自动回退 keyfile 口令）。此后本机启动/锁屏恢复时自动取回 KEK 解锁，免输口令。
  - **边界（必须写进 UI 提示）**：DPAPI 绑定的是"本机 + 当前 Windows 账户"，只能防止他人拷走 keyfile 文件后解密，**不能防御本机账户失陷**（已登录环境可调用 DPAPI）。因此：keyfile 导入/导出、口令修改等**敏感操作仍强制手输口令**；自动解锁仅在启动与日常锁屏恢复时生效，失焦自动锁默认仍可自动解锁（策略可关）。

**字段保留铁律实现**：`model.Entry` 结构体对已知字段强类型、未知字段收进 `Extra map[string]json.RawMessage`；序列化时先写 Extra 再覆盖已知字段。

**吊销参与流程（在线成员侧）**：由 syncer 自动完成（7.2 auto-rekey），无需用户点击确认；UI 仅在执行期间显示非阻塞"组密钥升级中"提示。

### 9.2 其余部分（从简）

- 页面：解锁页（含自动锁定倒计时提示）、树形浏览（项目→环境→IP类型→账号类型→账号 五层骨架 + 各层旁挂的 custom 补充卡片，支持筛选）、条目编辑（树形递归表单：account 用固定模板，custom 用**通用动态表单**按 custom_fields 自动生成输入项，含密码生成器一键填入）、**冲突解决页（Git 式三栏 diff，见下）**、设置页（同步状态、设备列表、keyfile 导入/备份、锁定策略、**服务端地址**）。**管理功能不在普通客户端中**——管理操作统一在独立**管理端**应用完成（§9.3）。

- **服务端地址配置与持久化（§9.2 新增约定）**：
  - 服务端地址+端口（如 `https://host:8443`）写入**客户端本地配置**；客户端带本地数据库（`client/core/store`）时**写入库中**（`app_config` 单行表），不落前端 localStorage（§14.1 前端禁存敏感数据；地址非敏感但统一走 Go 层持久化）。
  - **首次使用走完整初始化配置引导**：解锁页必填「服务端地址」→ 填写完成并**验证通过**（用设备 token 调心跳/同步探活，确认地址可达且鉴权有效）后进入主界面查看明文。
  - **后续启动不必重设配置**：从本地库自动带出上次地址，直接解锁进入。
  - **设置页可修改服务端地址和端口**：修改后需重新验证并重连（token 不变，直接换目标地址）。
  - **支持以附加参数方式重启初始化配置引导**（如 `pbcli unlock --reinit --server <new>` / UI 启动参数）：忽略已存配置，重新走首次引导。

- **无明文条目的展示位置**：`pending_entries`（等待信封）与 `bad_seq`（解密失败）条目没有明文（title/parent_id 都在密文里），**不参与树组装与列表展示**；仅在设置页"同步状态"区以 entry_id + seq + 状态（等待信封 / 同步异常）列出，解密成功后才进入树。

- **冲突解决页（Git 式）**：对冲突条目展示 **base / ours / theirs 三栏 diff**（字段级高亮）；每个冲突字段提供「采用本地 / 采用服务端 / 手动编辑」操作与 Git 式冲突标记预览；自动合并成功的字段直接显示为合并结果。解决后一次 push 落为新版本（§7.3）。

- UI 框架：Vue3 + Pinia + 任意组件库；所有敏感操作调用 Wails 绑定的 Go 方法，前端不触碰密钥。

- 本地备份：一键导出"密文包 + 我的信封"加密压缩包（同 §14.3 3.7）。

### 9.3 管理端（`client/app` 的 `--admin` 模式，Web 管理台永久弃用）

- **决策**：管理功能由**普通客户端的 `--admin` 模式**（`client/app`，Wails）承载，仅 role=admin 的用户使用。`--admin` 启动进入管理面板：与普通客户端同构（同一 keyfile/注册/认证体系），界面含管理功能，不含条目查看/编辑——**管理面板只做元数据操作，不接触 DEK 与私钥，不提供"查看明文"能力**；管理员可切回普通模式使用条目功能。不实现任何形式的服务端 Web 管理台。

- **理由**：管理动作全是元数据操作（建用户/加组/踢人/吊销/禁设备/查审计/触发 rekey），3-5 人团队频率极低；Web 管理台会把高权限 admin token 暴露到浏览器环境并多开公网登录面，收益不抵风险。管理面板随 `client/app` 一起构建（`--admin` 启动进入），管理界面只对 admin 分发。

**管理端功能**（全部走 §6.2 admin API）：

| 功能 | 接口 |
| --- | --- |
| 生成 keyfile（内嵌 keytool genuser，含注册凭证 attestation） | 本机离线完成，私钥不出管理端 |
| 创建用户（导入 pub.json，含注册凭证） | POST /admin/users |
| 吊销成员（需输入成员名二次确认） | POST /admin/users/:uid/revoke |
| keyfile 找回/换绑公钥 | POST /admin/users/:uid/keyfile-reset |
| 建组、加组成员 | POST /admin/groups、PUT /admin/groups/:gid/members |
| 移出组成员（一键） | DELETE /admin/groups/:gid/members/:uid |
| **组成员清单（每行：用户名 / 在线状态 / 在线 IP / 在线设备名称·机器名）** | GET /admin/groups/:gid/members |
| **触发预防性重加密（rekey）** | POST /admin/groups/:gid/rekey（置 pending_rekey，执行由在线成员完成） |
| **归档组（协作冻结，保留历史只读）** | POST /admin/groups/:gid/archive |
| **重启组（恢复同步）** | POST /admin/groups/:gid/unarchive |
| **设备列表（在线状态、last_ip、hostname）** | GET /admin/devices |
| 禁用单台设备 | POST /admin/devices/:did/disable |
| 审计日志查询 | GET /admin/audit |
| 组状态查看（pending_rekey / key_version / **archived**，观察 rekey 进度与归档状态；仅元数据不含密文） | GET /admin/groups |

**一键体验**：创建用户 + 加入组后，页面显示"密钥交接将自动完成（组内任一成员上线后 ~1s，SSE 推送）"；吊销/移出后，页面显示"已即时断权，数据重加密将在后台自动完成"；触发 rekey 后，页面显示"已发起，组密钥升级由在线成员后台完成，进度可刷新查看"。

**归档状态操作后果提示（管理端 UI 必须标明）**：组处于已归档状态时，管理端对相关操作的确认弹窗/操作区必须展示对应后果说明——

| 归档期操作 | 管理端提示文案（要点） |
| --- | --- |
| 归档（archive）本身 | "归档后该组协作冻结：成员不可写入、不产生新变更；历史数据保留且仍可只读查看（含新设备拉取）；可随时重启恢复" |
| 新增成员 | "该组已归档：成员关系立即生效，但密钥交接挂起——新成员在组重启前看不到任何数据；重启后自动补信封并可查看全部历史" |
| 吊销/移出成员 | "该组已归档：断权立即生效（token 失效、信封删除）；数据重加密挂起，将在组重启后由在线成员自动完成" |
| keyfile-reset（该组成员） | "该组已归档：换绑即时生效、旧设备全部作废；新公钥信封挂起——该用户在组重启并完成设备注册前看不到数据，重启后自动补齐、数据不丢" |
| 触发 rekey | "该组已归档：仅置位 pending_rekey，不执行；将在组重启后由在线成员自动收敛" |

组列表页对归档组显示"已归档"标记；归档组的成员管理操作不禁止，但必须先展示上述后果提示再允许确认。

**硬规则**：吊销、移出、触发 rekey 等操作必须二次确认（输入对象名称），且管理端在执行前先触发一次本地密文备份（管理端无条目，备份指导出当前服务端密文快照）。管理端永远只做元数据操作，不接触 DEK 与私钥，不提供任何"查看明文"能力（架构上也做不到）。

## 10. 密钥工具 CLI（完整）

```bash
keytool genuser --name zhangsan [--out ./zhangsan]
    # 生成 SM2 密钥对；交互式设置 keyfile 口令（不回显、二次确认、<12 位给强度警告）
    # 输出 zhangsan.key（口令加密私钥）+ zhangsan.pub.json（{name, sm2_public_key, attestation}）
    
    keytool pubkey --key zhangsan.key
    # 输入口令，显示/导出公钥（用于登记核对）
    
    keytool inspect --key zhangsan.key
    # 校验 keyfile 完整性（不解密内容，仅校验格式与 kdf 参数）
```

- 密钥工具**不联网**（CI 静态检查 import 列表无 net/http 等网络包）；输出文件权限 0600（Windows 下 ACL 收紧）。

- **keytool 是全系统唯一的密钥生成路径**，admin 在**管理面板**内操作（client/app 的 --admin 模式，UI 内嵌调用；也可单独用命令行）。DEK 的包裹/重包裹由客户端在线完成。

- **注册凭证**：keytool 需配置 `PB_REG_SECRET`（与服务端一致的部署级共享密钥），`genuser` 用它计算 pub.json 的 attestation（§4.4）；未配置或与服务端不一致时导入会被服务端拒绝。

- **移除 backup 命令**：服务端备份走 §12.3 cron，客户端备份走 §14.3 3.7。

## 11. 安全设计与威胁模型

| 威胁 | 缓解 |
| --- | --- |
| 服务端拖库 | 零知识：密文+信封，无 DEK/私钥，无法解密 |
| 中间人/窃听 | TLS1.3 + 证书 pinning；密文二次防护 |
| 服务端被控篡改/回滚数据 | 条目级 HMAC-SM3，客户端验证失败告警并拒绝 |
| token 泄露 | 只得密文；设备级禁用；30 天滑动过期 |
| keyfile 泄露 | keyfile 即身份：口令保护（PBKDF2-SM3 十万次）+ 安全通道转交 + 泄露后 admin 立即吊销并重发 |
| keyfile 丢失/口令遗忘 | admin 一键 keyfile-reset 换绑公钥，数据不丢 |
| 暴力破解 keyfile 口令 | PBKDF2-SM3 十万次迭代；客户端解锁失败 10 次延迟指数退避 |
| 成员离职 | 一键吊销即时断权 + 后台 auto-rekey；旧人只能读到离职前已有数据 |
| 恶意客户端上传脏数据 | 组权限/kv/大小校验；坏密文写入 bad_seq 跳过清单，不影响他人同步 |
| 设备丢失 | 本地私钥有 KEK 保护；禁用设备；吊销并重加密 |
| 无人值守/电脑被他人使用 | 窗口失焦 5 分钟自动锁定并 Wipe 内存密钥；解锁策略三选一（口令 / Windows Hello（三期 3.9）/ DPAPI 自动解锁） |
| 本机 DPAPI 自动解锁被滥用 | 仅限本机+当前账户；keyfile 导入/导出、口令修改等敏感操作强制手输口令；失陷账户前提下的防护以口令熵为准（DPAPI 只省输入，不降熵） |
| 密钥来源伪造（绕过 keytool） | 注册凭证 attestation 校验：非 keytool 生成（不持 PB_REG_SECRET）的公钥导入被拒（40001） |
| 推送通道伪造/重放 | SSE 通知仅含 seq 元数据与组 ID，不含密文；token 校验 + 每 token 最多 4 条订阅；数据以加密拉取为准 |
| 更新通道被篡改（三期 3.11） | 安装包 SM2 签名 + 客户端内置公钥验签 + SHA256 双校验；下载走 HTTPS；伪造包一律拒绝安装 |

**已知边界**（如实记录，不掩盖）：

1. **keyfile 即身份**：保管责任在个人；admin 转交必须走线下安全通道（U 盘/加密聊天），口令另走一条通道。

1. **旧人可读离职前已有数据**：任何 E2E 方案都无法收回已交付的明文；吊销后旧人无法再获得任何新数据（40301/40302，且新数据永不使用旧 DEK 加密）。

1. **auto-rekey/auto-wrap 依赖至少一名在线成员**：全员离线时该组新写入被本地挂起（不丢数据、不产生旧 DEK 新明文），有人上线后自动收敛（SSE 推送时 ~1s；离线端恢复后按启动拉取/回退轮询收敛）。管理端手动触发 rekey 同理——触发只是置位，执行仍等在线成员（§6.3）。

1. **重加密期间**，离线成员的未推送修改可能以"冲突副本"呈现，由本人选择保留。

1. 服务端可见元数据（数量、时间、大小、组代号、设备名、机器名、最近登录 IP、在线状态）。

1. 单条坏密文会触发跳过清单与告警，但不会泄露任何内容。

- 设计要求：§6.3 校验链顺序固定；批量 push 每条独立事务；审计由中间件统一写入；pull 默认 500 条按 seq 升序；墓碑清理每日一次；**/sync 计算 `pending_rekey` 与 `missing_envelopes`**；**信封保留/清理规则**（旧 kv 信封保留至全部条目到达新 kv；收尾判定排除墓碑，§7.4）；revoke/remove 单事务断权+删信封+置标记；**push/信封提交成功后经 SSE 通知相关组订阅者（通知仅含 seq 元数据）**；**/admin/users 校验注册凭证 attestation（PB_REG_SECRET）**；**冷启动：新建组无任何信封时，GET /sync 的 missing_envelopes 返回全部 active 成员，keys 入伙追加分支（kv=1）接收全集提交**；**中间件更新 devices.last_ip/last_seen；SSE 维护活跃连接表（device_id→心跳）用于在线判定**；**GET /admin/groups/:gid/members 与 GET /admin/devices（仅元数据，不含密文/信封）**；**归档/重启：archive 需组名二次确认、置 archived=1 并记 archived_at；归档组 push/keys 均拒收 40905、SSE 不推送、groups 标记 archived=true、不产生 missing_envelopes、历史 changes 与信封仍可拉取（只读）；unarchive 清除标记；审计记 archive/unarchive**。

- 验收用例（集成测试）：bootstrap→建用户→加组→**冷启动（首个在线成员生成 DEK kv=1 并包裹全集）**→auto-wrap→新人拉取解密；两用户两组全流程；push→pull 一致；过期 base_seq→40901 带服务端当前密文；旧 kv→40902；非成员→40302；>256KB→41301；非 admin→40303；删除→对端 pull 到 deleted=true；**revoke 后旧设备下一次请求→40301**；**rekey 中断（杀进程）后重跑收敛且无重复条目、旧信封在全部条目到达新 kv 后物理删除**；信封集合校验（非 active 成员/集合不完整/覆盖→40904）；错误码与 §13 全量对表；**A 端 push 后 B 端收到 SSE change 并在 1s 内自动拉取收敛**；**伪造 attestation 导入被 40001 拒收**；**admin 触发 /admin/groups/:gid/rekey → 组 pending_rekey 置位 → 在线成员 auto-rekey 收敛（kv+1）→ 再次触发幂等**；**组成员清单：在线端 online=true 且含 last_ip/hostname、SSE 断开后 60s 内判定离线**；**归档组：archive 后 push/keys 均拒收 40905、SSE 不推送、groups 标记 archived=true、历史 changes 与信封仍可拉取（只读），unarchive 后客户端检测 archived 翻转自动全量拉取恢复、挂起的 pending_rekey/missing_envelopes 正常收敛**。

- 设计要求：**core 不依赖任何 UI 框架，公开 API 输入输出均为可序列化结构**（§3.1）；keyfile 导入与设备注册（**注册上报 device_name 与 hostname**）；解锁失败 10 次起指数退避（1s→2s→…→5min）；DEK 缓存锁定/退出/hmac 连续失败 10 次全量 Wipe；syncer 单例互斥；**触发源：SSE 推送事件 / 本地变更事件 / 启动自动拉取 / 手动刷新；SSE 断线回退轮询（健康 5s、降级 30s + 指数退避）**；**启动/解锁后立即增量拉取补齐离线变更**；**auto-wrap：检测 missing_envelopes 自动包裹上传；冷启动：组内无信封时首个在线成员生成 DEK（kv=1）并包裹全部 active 成员（§7.2 3a）**；**auto-rekey：写挂起 + 崩溃可续 + 幂等（收尾判定排除墓碑）**；本地敏感列 SM4-GCM；**同步顺序：信封先于密文处理（§7.2），无对应 kv DEK 的条目暂存 pending_entries（不验 hmac、不进 bad_seq），信封到达后补处理**；**归档组处理：archived=true 时 changes/envelopes 正常入库（历史只读），跳过 auto-wrap/auto-rekey 且本地禁止编辑该组条目（UI 只读）；检测 archived 翻转（true→false）自动全量拉取恢复（§7.2 4d）**；**自动锁定：窗口失焦 5 分钟自动锁屏并 Wipe**；**自动解锁（Windows）：KEK 写入 DPAPI（TPM 保护），启动/锁屏恢复自动取回；keyfile 导入/导出与口令修改强制手输口令**；**密码生成器（crypto/rand，可配长度/字符集/排除易混字符）**；**冲突三路合并：编辑条目时保存 base 快照（local_entries.base_enc），40901 后用 base/ours/theirs 字段级合并，冲突字段标标记（§7.3）**。

- 验收用例（harness 脚本化）：双端同步一致；断网改 3 条→恢复按序 push；**rekey 批次拉取：kv+1 密文与新信封同批到达时正常收敛（信封先处理），无条目误入 bad_seq**；**信封未到的密文暂存 pending_entries，信封到达后自动补解密入库**；**冲突三路合并：A、B 同改不同字段→自动合并无冲突一次成功；A、B 改同一字段不同值→冲突标记、逐字段解决后 push**；**admin 建新用户加组 → 新人拿到信封并可解密（无手工操作）**；**新建组冷启动：首位在线成员自动生成 DEK（kv=1）并包裹全部成员，其余成员拉到信封即可解密**；**revoke → 旧设备 40301、剩余成员自动重加密、重加密完成前组写挂起**；kv 过期→自动重加密重推成功；未知字段保留；篡改条目被 hmac 拒绝；**失焦 5 分钟后锁屏且内存密钥清零；密码生成器输出符合配置的字符集与长度**；**A 端修改后 B 端 ≤1s 内自动拉取并可见（SSE 推送）**；**客户端关闭后重启/解锁，启动即自动拉取离线期间的变更并收敛**；**SSE 断线 → 回退轮询仍收敛 → 重连后恢复推送**；**DPAPI 自动解锁：写入后重启免输口令解锁、keyfile 导入仍强制口令（Windows 实机）**；**设备注册后服务端 devices 表含 hostname/last_ip，成员清单接口返回正确在线状态**。

- 验收：下方 16 条场景 16/16 通过；问题全部录 issue 分级（P0 不过夜）。

**一期验收场景清单（1.9 用，逐条打勾）**：

1. 首启 bootstrap：admin 用 keytool 生成自己 keyfile → 用首启 token 建立首个 admin。

1. admin 一键创建新用户（导入 pub.json）并加入组 → 新人导入 keyfile 解锁，**自动收到信封并解密全部条目（SSE 推送 ~1s）**，**无需任何老人手工操作**。

1. A 端新增/修改条目，**SSE 推送 ~1s 内** B 端可见且内容一致。

1. A 断网修改 3 条 → 恢复后按序 push；期间 B 也改了其中 1 条 → A 端触发**三路合并**：B 改的字段与 A 不同 → **自动合并一次成功**；同一字段不同值 → **Git 式冲突标记，逐字段解决后 push**（§7.3）。

1. A 删除条目 → B 端收到墓碑并移入回收站；B 端不会把该条目当新数据回传。

1. admin 一键吊销/移出成员 → 该成员 token 即刻失效（40301/40302）；在线成员 **~1s 后台 auto-rekey（推送驱动）**；**重加密完成前该组新写入挂起**；被移除成员拉不到任何新数据。

1. **全员离线时吊销** → 组写挂起、无旧 DEK 新明文外流；任一成员上线后自动收敛，旧 kv 信封在条目全部更新后物理删除。

1. 篡改服务端数据库中某条密文一个字节 → 两端客户端均 hmac 告警并拒绝入库。

1. 锁屏/退出后内存中私钥与 DEK 已清零。

1. 客户端窗口失焦 5 分钟 → 自动锁屏且内存密钥清零；密码生成器可生成符合配置的随机密码并填入条目编辑页。

1. 客户端启动/解锁后**立即自动拉取**上次离线期间的变更并收敛。

1. A 端修改条目 → 服务端 SSE 推送 → B 端 **≤1s** 内自动拉取并可见；SSE 断线时回退轮询仍收敛、重连后恢复推送。

1. **管理端触发预防性 rekey**（POST /admin/groups/:gid/rekey）→ 组 pending_rekey 置位 → 在线成员 ~1s 后台换钥收敛（kv+1、重加密、删旧信封）→ 管理端观察到 key_version 递增且 pending_rekey 清除；全员离线时保持置位、上线后自动收敛。

1. **DPAPI 自动解锁**（Windows）：开启后重启/锁屏恢复免输口令自动解锁，内存密钥经 DPAPI(TPM) 取回；keyfile 导入/导出、口令修改仍强制手输口令；关闭开关后立即失效。

1. **管理端组成员清单**：每行显示 用户名/在线状态/在线 IP/在线设备名·机器名（GET /admin/groups/:gid/members）；成员在线时 online=true 且带 IP 与设备名，退出客户端后 ≤60s 变离线。

1. **归档/重启组**：admin 归档组（组名二次确认）→ 该组 push/keys 拒收 40905、SSE 不推送、客户端跳过全部协同（auto-wrap/auto-rekey 冻结）、历史 changes 与信封仍可拉取（新设备只读查看）、成员本地数据可看；重启（unarchive）→ 客户端检测 archived 翻转自动全量拉取并恢复同步，归档期间挂起的 pending_rekey/missing_envelopes 正常收敛；归档期间组成员关系/信封/密文保留、revoke 即时断权有效。

**一期设计要求（施工硬规范，违反即返工）**：

安全不变量（最高优先级）：

1. 服务端代码中禁止出现任何明文敏感字段的类型定义、变量与日志；code review 逐项核对。

1. 私钥、DEK、KEK 一律用 `[]byte` 驻留内存，使用后立即覆写清零；禁止用 string 承载密钥材料。

1. 所有随机数只能来自 `crypto/rand`；禁止 `math/rand` 出现在任何安全相关路径（lint 规则强制）。

1. 密钥不跨层：前端 JS 层禁止出现私钥/DEK/KEK，Wails 绑定方法不得返回密钥本身。

1. 日志脱敏：任何日志不得包含 ciphertext、token、密钥材料、hmac 之外的安全敏感内容。

1. **任何新数据加密必须使用组当前 kv 的 DEK**（写挂起不变量，见 §7.2）。

工程规范：

1. wire format 全部带 `v` 版本字段；解析器必须前向兼容（跳过不认识的字段）。

1. store 层接口化（`type Store interface`），时间源与随机源依赖注入。

1. 所有 SQL 参数化；所有 HTTP handler 带 context 超时（默认 10s）；错误不吞、不裸 panic。

1. 依赖准入：新增第三方依赖需在 PR 说明许可证与维护状态；优先标准库。

1. 性能基线（局域网）：pull 500 条 ≤ 1s；单条 push ≤ 200ms；解锁（PBKDF2 10 万次）≤ 1.5s；同步空闲内存占用 ≤ 150MB。

**一期完整验收标准**：

- 功能：上方 16 条端到端场景逐条实机通过。

- 测试：单测+集成测试 CI 全绿；`go test -race ./...` 无数据竞争告警；覆盖率达标（crypto ≥90%，server ≥80%）。

- 安全：安全不变量 1-6 逐条人工核对记录；`gosec ./...` 无高危；`go vet` 零告警。

- 性能：性能基线第 11 条逐项实测达标并记录。

- 部署：干净机器 `docker compose up` 一条命令拉起；备份→删库→恢复演练通过；首启 bootstrap 流程跑通。

- 文档：实现与 §4/§5/§6/§7 描述一致；CHANGELOG 完整；打 `v0.1.0` tag。

### 15.2 admin 建用户 + auto-wrap（入伙）

```text
管理端(内嵌 keytool): genuser --name zhangsan
    → zhangsan.key + zhangsan.pub.json {name:"zhangsan", sm2_public_key:"...", attestation:"..."}
    C(admin): POST /api/v1/admin/users   {name:"zhangsan", sm2_public_key:"...", attestation:"..."}
    S: {"user_id":"u1"}
    C(admin): PUT /api/v1/admin/groups/g1/members   {user_id:"u1"}
    S: 200
    
    # 任一在线成员客户端下一轮同步：
    C: GET /api/v1/sync?since=...   (X-Key-Versions: g1:1)
    S: {"server_seq":..., "changes":[...], "key_envelopes":[...],
    "groups":[{id:"g1", key_version:1, pending_rekey:false, missing_envelopes:["u1"]}]}
    → 客户端: 用 g1 的 DEK 包裹 u1 的公钥
      （若 g1 为新建组、尚无任何信封 → 冷启动：该在线成员先生成 DEK(kv=1)，
        再为全部 active 成员包裹）
    C: POST /api/v1/groups/g1/keys   {key_version:1, envelopes:[{user_id:"u1", wrapped_dek:"..."}]}
    S: 200
    
    # 新人导入 keyfile 后：
    C: POST /api/v1/auth/device-challenge  {user_id:"u1"}
    S: {"challenge":"...","expires_in":300}
    C: POST /api/v1/auth/device  {user_id:"u1", device_name:"zhangsan-mbp", challenge:"...", signature:"..."}
    S: {"device_id":"d1","token":"t...","expires_in":2592000}
    C: GET /api/v1/sync?since=0
    S: {"server_seq":..., "changes":[...全部条目...],
    "key_envelopes":[{group_id:"g1", key_version:1, wrapped_dek:"我的信封"}],
    "groups":[{id:"g1", key_version:1, pending_rekey:false, missing_envelopes:[]}]}
    → 本地: 私钥解信封得 DEK → 验 hmac → 解密 → 入库
```

### 15.3 吊销 + auto-rekey（退出）

```text
C(admin): POST /api/v1/admin/users/u2/revoke
    S: 200   # 单事务：token 失效、删 u2 全部信封、移除组成员、g1.pending_rekey=1
    
    # 在线剩余成员客户端下一轮同步：
    C: GET /api/v1/sync?since=...
    S: {"groups":[{id:"g1", key_version:1, pending_rekey:true, ...}]}
    → 客户端 auto-rekey：
    1) 挂起 g1 新写入
    2) 用旧 DEK 解密全部条目
    3) 生成新 DEK（kv=2），向全部 active 成员包裹
    C: POST /api/v1/groups/g1/keys   {key_version:2, envelopes:[{u0,...},{u1,...}]}
    S: 200   # g1.key_version=2，保留 kv=1 旧信封（条目未全部到 kv2）
    C: POST /api/v1/sync/push        {mutations:[{entry_id:"e1",group_id:"g1",base_seq:100,
                                     key_version:2, ciphertext:"{kv:2,...}", ...}, ...]}
    S: {"results":[{"entry_id":"e1","ok":true,"new_seq":...}, ...]}
    # push 事务内检测到全部条目已到 kv2 → 删除 kv1 旧信封
    → 解除 g1 写挂起
    
    # 被吊销者任何请求：
    C: GET /api/v1/sync?since=...
    S: 40301
```

### 15.4 常规同步

```text
C: GET /api/v1/sync?since=0           Authorization: Bearer t...

       base_seq:0,key_version:1,ciphertext:"{v:1,alg:SM4-GCM,...}"}]}
    S: {"results":[{"entry_id":"e1","ok":true,"new_seq":1}]}
    
    另一台设备:
    C: GET /api/v1/sync?since=0

    "groups":[{id:"g1", key_version:1, pending_rekey:false, archived:false, missing_envelopes:[]}]}
    → 本地: 私钥解信封得 DEK → 验 hmac → 解密 → 入库 → last_seq=1
```
